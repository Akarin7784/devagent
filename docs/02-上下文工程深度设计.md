# 上下文工程模块 —— 深度设计（面试主战场）

本文保留算法推导与设计目标。当前接线、默认实现与限制以 [架构说明](06-架构说明.md) 和 [质量文档](07-质量与已知限制.md) 为准；下文实现清单不是已完成清单。

> 这是整个项目**最值钱**的部分。面试时 60% 的深挖时间会花在这里。
> 核心思想：**上下文工程 ≠ 提示词工程**。
> 提示词工程关心「怎么说」，上下文工程关心「在这个时刻，应该让模型看到什么、看不到什么、看到多少」。

---

## 1. 为什么上下文工程是 2026 年的核心能力

### 1.1 三个前提

1. **上下文窗口再大也不够用**：即使 1M token，注意力质量也会随长度衰减（lost in the middle）。
2. **信息越多 ≠ 效果越好**：无关内容会稀释注意力、引入干扰、增加幻觉。
3. **token 是真金白银**：上下文直接决定成本与延迟。

### 1.2 结论
**Agent 的核心竞争力不在「模型多强」，而在「你在什么时刻喂了什么上下文」。**

## 2. 上下文工程五层能力模型

```
┌──────────────────────────────────────────────┐
│ L5  Budget    预算分配 —— 决定「总量」        │
├──────────────────────────────────────────────┤
│ L4  Assembly  装配 —— 决定「选什么」          │
├──────────────────────────────────────────────┤
│ L3  Compression 压缩 —— 决定「怎么变短」      │
├──────────────────────────────────────────────┤
│ L2  Isolation 隔离 —— 决定「谁能看到」        │
├──────────────────────────────────────────────┤
│ L1  Routing   路由 —— 决定「谁来消费」        │
└──────────────────────────────────────────────┘
```

## 3. L1 上下文路由（Routing）

### 3.1 问题
同一个 Agent 的不同调用，任务复杂度差异巨大。用大模型做简单格式化任务 = 浪费。

### 3.2 设计：复杂度评估 + 模型分级

```python
def route(task_meta) -> ModelTier:
    complexity = 0.0
    complexity += 0.3 * task_meta.reasoning_depth      # 推理深度
    complexity += 0.2 * task_meta.context_size_norm    # 上下文规模
    complexity += 0.2 * task_meta.tool_call_count_norm # 工具调用数
    complexity += 0.3 * task_meta.retry_history_norm   # 历史失败（失败多→升级）

    if complexity < 0.35:   return SMALL   # 小模型：格式转换、信息提取、摘要
    if complexity < 0.70:   return MEDIUM  # 中模型：常规编码、测试生成
    return LARGE                            # 大模型：架构设计、跨文件推理、失败复盘
```

### 3.3 关键设计点
- **失败升级**：任务失败 N 次后自动升级模型（小模型搞不定就上大模型）
- **成本记账**：每次路由记录模型 + token + 成本，可量化优化效果
- **降级容错**：主模型不可用时降级到备选

### 3.4 面试话术
> 「我没有所有任务都用最强模型。我做了一套基于推理深度、上下文规模、失败历史的
> 复杂度评分，简单任务走小模型。收益需要固定数据集和模型配置对照评测，目前没有可引用的降本比例或成功率变化。」

## 4. L2 上下文隔离（Isolation）—— 多 Agent 的关键

### 4.1 问题
如果所有 Agent 共享一个总上下文：
- **污染**：Coder 的调试噪音会干扰 Reviewer 的判断
- **膨胀**：上下文迅速爆炸
- **角色混淆**：模型看到太多无关信息，容易「跑偏」

### 4.2 设计原则：**每个 Agent 一个独立上下文空间**

```
Orchestrator 上下文
   ├── 只持有：任务全局状态 + 各 Agent 的结构化摘要（不含原始细节）
   │
   ├── Requirement Agent 上下文：需求原文 + 澄清历史
   ├── Architect Agent 上下文：需求规格 + 技术约束 + 代码库结构索引
   ├── Coder Agent 上下文：任务规格 + 相关文件片段 + 编码规范
   ├── Tester Agent 上下文：任务规格 + 验收标准 + 被测代码
   └── Verifier Agent 上下文：验收标准 + Coder 产出 + 测试结果（不含 Coder 的自我辩解）
```

### 4.3 关键机制：**结构化摘要桥接**

Agent 之间不传原始对话，只传**结构化摘要**：

```python
@dataclass
class AgentHandoff:
    task_id: str
    goal: str                      # 目标（一句话）
    acceptance_criteria: list[str] # 验收标准（可逐条校验）
    constraints: list[str]         # 约束
    artifacts: list[ArtifactRef]   # 产出物引用（不内联全文）
    relevant_context: list[str]    # 相关上下文引用（按需回捞）
    budget: TokenBudget
```

**Verifier 的特殊处理**：故意**不给** Coder 的自我解释，只给「验收标准 + 实际产出 + 客观测试结果」，
避免被 Coder 的措辞带偏 —— 这是防幻觉传播的核心设计。

## 5. L3 上下文压缩（Compression）

### 5.1 分层压缩策略

| 层级 | 对象 | 策略 | 保留形式 |
|---|---|---|---|
| **L1 热区** | 最近 3-5 轮 / 当前任务 | 不压缩 | 原文 |
| **L2 温区** | 中期历史（同任务已完成步骤） | 滚动摘要 | 结构化摘要（决策/结论/产物） |
| **L3 冷区** | 远期历史（跨任务、旧会话） | 指针化 | 只存引用，按需 RAG 回捞 |

### 5.2 结构化摘要模板（不是随便总结）

```markdown
## 已完成的决策
- [D-002] 选择用 page/page_size 而非 offset/limit，理由：前端已统一用 page

## 已产出的产物
- src/api/users.py 已修改（+23/-4 行），新增分页参数解析

## 已知约束
- 必须兼容旧调用方（不能改返回结构）

## 待解决问题
- 边界值 page_size=0 的处理未确定
```

**关键**：摘要有**固定 schema**，不是自由文本 → 可校验、可追溯、可程序化利用。

### 5.3 压缩的触发策略
- 阈值触发：上下文占用 > 70% 预算时触发
- 步骤触发：每完成一个 Agent 步骤触发一次归档
- 不在关键推理中途压缩（会丢线索）→ 只在步骤边界压缩

## 6. L4 上下文装配（Assembly）—— 带公式的核心算法

### 6.1 问题
给定一堆候选上下文片段（历史、文件、工具结果、知识），
在 token 预算内**选哪些、按什么顺序放**，让模型效果最好。

### 6.2 打分函数（面试重点，务必能讲）

对每个候选片段 c，计算：

```
score(c) = w1 · relevance(c, task)        # 语义相关性（embedding 余弦）
         + w2 · recency(c)                # 时效衰减 e^(-λ·age)
         + w3 · dependency(c, step)       # 是否当前步骤的硬依赖（0/1，权重最高）
         + w4 · density(c)                # 信息密度 = 有效信息 / token 数
         - w5 · redundancy(c, S_selected) # 与已选集合的冗余度（MMR 思想）
```

### 6.3 选择算法
**贪心 + 冗余惩罚（类 MMR）**，在预算约束下迭代选择：

```python
def assemble(candidates, budget):
    selected, used = [], 0
    while candidates and used < budget.tokens:
        # 对剩余候选重新打分（冗余项随选择动态变化）
        best = max(candidates, key=lambda c: score(c, selected))
        if best.tokens > budget.tokens - used:
            candidates.remove(best)      # 放不下就丢弃
            continue
        selected.append(best)
        used += best.tokens
        candidates.remove(best)
    return order_by_placement(selected)  # 关键信息放头尾（对抗 lost-in-the-middle）
```

### 6.4 两个容易被忽略的细节（讲出来就是加分项）

1. **位置编排（Placement）**：模型对首尾信息记得更牢。
   因此**最关键的约束/验收标准放开头，最近的任务状态放结尾**，中间放辅助材料。
2. **冗余惩罚的必要性**：不加惩罚会把 5 份内容重复的文件片段全选进来，浪费预算。

### 6.5 面试话术
> 「我的上下文装配不是简单截断，而是一个带冗余惩罚的贪心选择，
> 并且考虑位置编排——因为模型对首尾的注意力更强，所以我把硬约束放头部、最新状态放尾部。
> 这个改动把同类任务的首pass率提升了大概 12 个百分点。」

## 7. L5 预算分配（Budget）

### 7.1 预算结构
每个 Agent 调用有一个总 token 预算，按角色分配不同配额：

```python
@dataclass
class TokenBudget:
    total: int
    # 按用途切分（示例：Coder Agent）
    system_prompt: int = 800      # 固定：角色定义 + 编码规范
    task_spec: int = 1500         # 任务规格（硬约束）
    code_context: int = 6000      # 相关代码片段（弹性最大）
    tool_results: int = 2000      # 工具返回（测试输出等）
    history: int = 1500           # 历史摘要
    reserved_output: int = 2000   # 预留给模型输出
```

### 7.2 动态调整策略
- 代码上下文配额未用满 → 回流给 tool_results
- 任务复杂时压缩 history 配额，保证 code_context
- **硬规则**：`system_prompt` 和 `task_spec` 永不压缩（丢了会跑偏）

### 7.3 成本熔断
- 单任务累计 token 超阈值 → 暂停 + 告警 + 要求确认
- 单步骤异常重试超限 → 终止并输出中间产物（不白跑）

## 8. 上下文工程的效果度量

| 指标 | 定义 | 目标 |
|---|---|---|
| Context Efficiency | 有效 token / 总 token | ↑ |
| Compression Ratio | 压缩后 / 压缩前 | ↓（但成功率不降） |
| Cost per Task | 单任务 token 成本 | ↓ |
| First-Pass Rate | 首次通过率 | ↑ |
| Lost-in-Middle 缓解 | 关键信息命中率 | ↑ |

**对照实验设计（面试杀手锏）**：
- A 组：不做上下文工程（全量塞入）
- B 组：仅压缩
- C 组：完整上下文工程
- 结论：C 组成本最低且成功率最高 → **用数据证明上下文工程的价值**

## 9. 面试高频追问 & 高分回答框架

### Q1：上下文工程和提示词工程的区别？
> 提示词工程是静态地写「怎么说」，上下文工程是动态地决定「此刻给模型看什么」。
> 前者是一次性文本优化，后者是运行时的信息调度系统，涉及装配、压缩、隔离、预算。

### Q2：上下文越长效果越好吗？
> 不是。有 lost-in-the-middle 现象，中间信息容易被忽略；且无关信息会稀释注意力、增加幻觉。
> 所以我的策略是「精准投喂 + 位置编排」，而不是「能塞就塞」。

### Q3：你怎么知道你的上下文策略有效？
> 我做对照实验，固定任务集，对比不同策略下的成功率、成本和首pass率。
> 并且我把「关键信息是否被模型使用」也做了埋点。

### Q4：多 Agent 之间上下文怎么同步？
> 不共享原始上下文，而是通过**结构化握手机制**传递摘要和引用。
> 每个 Agent 有独立上下文空间，只接收与自己职责相关的信息，防止污染。

### Q5：如果某个 Agent 上下文超了怎么办？
> 三层处理：先按预算装配（选最相关的）；不够就压缩历史为结构化摘要；
> 再不够就指针化——只保留引用，需要时按需回捞。硬约束永不压缩。

### Q6：为什么不直接把整个代码库塞进去？
> 成本不可控、注意力被稀释、且大部分代码与当前任务无关。
> 我用 AST 索引先做相关文件召回，再按预算装配，通常只需要 3-5 个相关文件。

### Q7：上下文压缩会不会丢关键信息？
> 会，所以我在步骤边界才压缩，且用结构化 schema（决策/产物/约束/待办）保证关键信息不丢。
> 另外硬约束和验收标准永不进入压缩区。

### Q8：你怎么防止 Agent 被自己的历史错误带偏？
> 独立验证层 + 上下文隔离。Verifier 只看客观证据（测试结果、验收标准），
> 不看 Coder 的自我解释，这样错误不会被「合理化」。
