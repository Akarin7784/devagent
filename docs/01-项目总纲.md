# DevAgent —— 多 Agent 协作的软件研发助手（项目总纲）

> 一句话定位：一个由多个专职 Agent 协作、以**上下文工程**为核心竞争力的软件研发助手，
> 输入一句需求（或一个 Issue），自动完成「需求澄清 → 方案设计 → 编码 → 测试 → 代码审查」全流程，
> 并具备完整的**可靠性保障、成本控制与评测体系**。

---

| 面试官关注点 | 本项目的回答 |

**一句话卖点**：市面上的 Agent demo 都在演示「Agent 能干活」，
我的项目解决的是「Agent 干得不稳、不可控、不可评估、太贵怎么办」—— 这才是生产级问题。

## 1. 核心问题（要解决什么）

### 1.1 表层问题
让 AI 自动完成一个完整的研发小任务（如「给这个 API 加一个分页参数并补测试」）。

### 1.2 真正的问题（这才是深度所在）
单 Agent 做长任务时会遇到四个天花板：

1. **上下文天花板**：代码库、历史对话、工具结果迅速塞满窗口 → 模型开始「遗忘」和「迷失」（lost in the middle）
2. **能力天花板**：一个 prompt 同时要求「理解需求 + 设计 + 写代码 + 写测试 + 自我审查」→ 每项都做不精
3. **可靠性天花板**：任何一步幻觉会沿链条传播，最终产出错了却"看起来对"
4. **成本天花板**：反复重试 + 全量上下文 → token 爆炸

**本项目的解法 = 用多 Agent 做能力解耦 + 用上下文工程做信息精准投喂 + 用验证层阻断幻觉传播 + 用路由做成本控制。**

## 2. 系统架构

### 2.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  交互层  Web UI（任务创建 / 实时进度 / 协作可视化 / Diff 展示）  │
├──────────────────────────────────────────────────────────┤
│  编排层  Orchestrator（状态机 / 任务分解 / Agent 调度 / 中断恢复）│
├──────────────────────────────────────────────────────────┤
│  Agent 层                                                │
│   Requirement │ Architect │ Coder │ Tester │ Reviewer      │
│        └─────── Verifier（独立验证，阻断幻觉传播）────────┘      │
├──────────────────────────────────────────────────────────┤
│  上下文工程层（本项目核心）                                  │
│   Context Assembly │ Compression │ Isolation │ Budget      │
├──────────────────────────────────────────────────────────┤
│  工具层  CodeSandbox / GitOps / LSP索引 / FileSystem / Test  │
├──────────────────────────────────────────────────────────┤
│  模型层  Model Router（DeepSeek / 通义 / 智谱 分级路由）      │
├──────────────────────────────────────────────────────────┤
│  基础设施  状态持久化 / 事件总线 / 全链路追踪 / 评测中台       │
└──────────────────────────────────────────────────────────┘
```

### 2.2 Agent 拓扑（Hierarchical + Verifier）

采用 **Supervisor 分层拓扑 + 独立验证层**，而非简单的 Peer-to-Peer：

```
                    ┌─────────────┐
                    │ Orchestrator│  ← Supervisor：只做规划与调度，不写代码
                    └──────┬──────┘
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │Requirement│   │ Architect│    │  Coder   │
    │   Agent   │   │  Agent   │    │  Agent   │
    └──────────┘    └──────────┘    └────┬─────┘
                                         │ 产出
                    ┌────────────────────┼────────────────────┐
                    ▼                    ▼                    ▼
              ┌──────────┐        ┌──────────┐        ┌──────────┐
              │  Tester  │───────▶│ Verifier │◀───────│ Reviewer │
              │  Agent   │  验证   │  Agent   │  验证   │  Agent   │
              └──────────┘        └────┬─────┘        └──────────┘
                                       │ 不通过 → 带反馈回退给 Coder
                                       ▼
                                   通过 → 交付
```

**为什么这样设计**（面试要讲）：
- **Orchestrator 不干活**，只规划调度 → 避免「又当运动员又当裁判」
- **Verifier 独立于干活者** → 用不同的模型/prompt 做交叉验证，这是阻断幻觉传播的关键
- **Coder 可被多个下游质疑并回退** → 形成带反馈的迭代闭环（Reflexion 思想）

### 2.3 核心数据流

```
需求文本
  → [Requirement Agent] 澄清 → 结构化需求规格（含验收标准）
  → [Architect Agent]   设计 → 技术方案 + 任务分解（DAG）
  → 对 DAG 每个叶子任务并行/串行派发给 [Coder Agent]
  → [Tester Agent]  写测试并在沙箱执行
  → [Verifier Agent] 交叉验证（测试是否真覆盖需求？代码是否真满足？）
  → [Reviewer Agent] 代码质量审查
  → 任一环节失败 → 带上下文反馈回退（限重试次数）
  → 通过 → 产出 Patch + 测试报告 + 审查意见
```

## 3. 上下文工程（本项目的核心竞争力模块）

这是**整个项目最该做深、最该在面试里重点讲**的部分。

### 3.1 五大子能力

| 能力 | 解决什么问题 | 关键设计 |
|---|---|---|
| **Context Assembly（装配）** | 该给这个 Agent 看什么？ | 按 Agent 角色定义「上下文模板」，只注入相关片段 |
| **Context Isolation（隔离）** | 子 Agent 互相污染 | 每个 Agent 独立上下文空间，只接收上游的**结构化摘要**而非原始对话 |
| **Context Compression（压缩）** | 历史太长塞不下 | 滚动摘要 + 关键信息抽取 + 引用式回指（只存指针不存全文） |
| **Context Budget（预算）** | token 成本失控 | 按 token 预算动态分配：系统指令 / 任务 / 证据 / 历史 各占配额 |
| **Context Routing（路由）** | 大材小用 | 按任务复杂度选模型，简单任务走小模型 |

### 3.2 关键算法：上下文预算分配（面试深挖点）

不是简单地「截断最早的对话」，而是**打分式装配**：

```
score(chunk) = w1 · relevance(chunk, task)      # 与当前任务的相关性
             + w2 · recency(chunk)              # 时效性衰减
             + w3 · dependency(chunk, step)     # 是否为当前步骤依赖
             + w4 · information_density(chunk)  # 信息密度（去冗余后）
             - w5 · redundancy(chunk, selected) # 与已选内容的冗余度

在 token 预算约束下，做带冗余惩罚的贪心/背包选择
```

**这段能讲清楚，面试官基本会认定你真做过。**

### 3.3 上下文压缩策略（分层）

- **L1 原文**：最近 N 轮 / 当前任务直接相关 → 保留全文
- **L2 摘要**：中期历史 → 滚动摘要（带结构的：决策/结论/待办）
- **L3 指针**：远期历史 → 只存「发生过什么」的引用，需要时按需回捞（RAG 式）

### 3.4 结构化握手机制（Agent 间通信）

Agent 之间**不传自然语言长文**，而是传**强类型结构化消息**：

```json
{
  "from": "architect",
  "to": "coder",
  "type": "task_spec",
  "payload": {
    "task_id": "T-003",
    "goal": "为 /users 接口增加分页参数",
    "acceptance_criteria": ["支持 page/page_size", "非法参数返回 400", "有单测覆盖"],
    "constraints": ["不改动现有返回结构", "必须兼容旧调用"],
    "relevant_files": ["src/api/users.py", "tests/test_users.py"],
    "context_refs": ["decision://D-002", "schema://user_model"]
  },
  "context_budget": {"max_tokens": 8000}
}
```

**好处**：可校验、可追踪、可压缩、防歧义 —— 这是「工程化」和「demo」的分界线。

## 4. 可靠性设计（面试重点）

### 4.1 幻觉传播阻断
- **独立验证层**：Verifier 用不同模型 + 不同 prompt 交叉验证，不信任 Coder 的自陈
- **证据链要求**：Coder 必须给出「改动理由 + 对应验收标准」，无法对应则打回
- **测试即事实**：沙箱里跑过的测试结果是唯一可信的成功信号，而非 Agent 说「我做完了」

### 4.2 长任务状态管理
- **Checkpoint**：每个步骤的输入/输出/状态持久化，崩溃后可从断点续跑
- **幂等重试**：重试不产生副作用（沙箱隔离 + 状态快照）
- **成本熔断**：单任务 token 超过阈值自动暂停并告警，防跑飞

### 4.3 失败反思（Reflexion）
失败不是简单重试，而是：
```
失败 → 分析失败原因（测试输出/报错栈）→ 生成「教训」
    → 教训写入下次尝试的上下文（避免重复踩坑）
    → 重试（带教训）
```

### 4.4 死锁与循环检测
- 回退次数上限 + Agent 循环检测（A 推给 B，B 又推回 A）
- 相同失败连续 N 次 → 升级策略（换模型 / 换方案 / 人工介入）

## 5. 成本与性能工程

| 手段 | 效果 |
|---|---|
| **模型分级路由** | 简单任务（格式转换、提取）走小模型，复杂推理走大模型 → 成本可降 5-10x |
| **语义缓存** | 相似请求命中缓存（embedding 相似度）→ 减少重复调用 |
| **上下文压缩** | 减少输入 token → 直接降本 + 降低延迟 |
| **并行执行** | DAG 中无依赖的任务并行 → 降总延迟 |
| **流式输出** | SSE 流式 → 用户感知延迟大幅降低 |
| **Prompt 缓存** | 固定前缀命中厂商 prompt cache（如支持） |

**面试话术**：「我不是把它做出来就行，我做了成本量化——单任务平均 token 从 X 降到 Y，
关键在模型路由和上下文压缩。」

## 6. 评测体系（Eval-driven，拉开差距的关键）

### 6.1 为什么必须有
AI 系统最大的坑是「改了 prompt 不知道变好还是变坏」。必须有量化评测。

### 6.2 评测设计

**任务级指标**
- 任务成功率（Task Success Rate）
- 首次通过率（First-Pass Rate）
- 平均回退次数
- 平均 token / 平均耗时

**轨迹级指标（Agent 专属，面试加分项）**
- 步骤合理性（是否走了冗余弯路）
- 工具调用准确率
- 上下文效率（有效 token 占比）

**质量级指标**
- 测试通过率
- 代码审查问题密度
- 需求覆盖率（验收标准是否逐条满足）

### 6.3 评测流水线
```
Golden Set（50-100 个标准化研发任务）
  → 自动执行
  → 多维度打分（规则 + LLM-as-Judge）
  → 生成报告 + 与历史版本对比
  → CI 集成：每次改动自动跑，防止回退
```

### 6.4 LLM-as-Judge 的偏差治理（深挖点）
- Judge 模型本身有位置偏差、长度偏好 → 用 **双向评估（换序再评一次）** 抵消
- 多 Judge 投票 + 人类标注校准
- **能聊这个的候选人极少**

## 7. 技术栈选型（含「为什么不用 XX」）

| 层 | 选型 | 理由 / 取舍 |
|---|---|---|
| 后端框架 | **FastAPI** | 原生 async + Pydantic 强类型校验，适合 Agent 编排 |
| Agent 编排 | **自研状态机**（参考 LangGraph 思想，不直接用黑盒） | 面试可讲原理；需要精确控制重试/token 预算 |
| 状态持久化 | **PostgreSQL** + 事件表 | 任务状态、Agent 事件、检查点。选 Postgres 而非 Mongo：需要事务与结构化查询 |
| 向量检索 | **pgvector** | 复用 Postgres，少一套基础设施。为什么不用 Milvus：数据规模不到，运维成本不值 |
| 消息/事件 | **Redis Stream**（起步）→ Kafka（扩展） | 起步轻量，架构预留升级路径 |
| 沙箱 | **Docker** + 资源限制 | 代码执行必须隔离。为什么不用 microVM：复杂度与收益暂不匹配（可作演进方向讲） |
| 代码解析 | **Tree-sitter**（AST） | 比正则靠谱，能精确定位符号与依赖 |
| 可观测 | **OpenTelemetry** + 自研 LLM span | 追踪每次 LLM 调用 / 工具调用 / token / 延迟 |
| 模型接入 | **DeepSeek + 通义 + 智谱**（统一抽象层） | 国内可用的同时做**多模型抽象**，便于路由与故障切换 |
| 前端 | **React + TypeScript + Vite** | 实时进度用 WebSocket/SSE；协作可视化为 DAG 图 + 时间线 |
| 评测 | 自研（参考 RAGAS / TruLens 思路） | 自研更能体现理解深度 |

**关键选型论点（面试必被问）**：
- 为什么自研编排而不用 LangChain/LangGraph？→ 需要精确控制上下文预算、重试策略、可观测埋点；黑盒框架在调试和成本控制上是负担。
- 为什么用结构化消息而不是自然语言传递？→ 可校验、防歧义、可压缩、可追踪。

## 8. 数据模型（核心表）

```sql
-- 任务
task(id, goal, status, created_at, total_tokens, total_cost, parent_task_id)

-- 执行步骤（DAG 节点）
task_step(id, task_id, agent_type, status, attempt, input_ctx_ref,
          output, error, started_at, finished_at, tokens, model)

-- Agent 事件（全链路追踪）
agent_event(id, step_id, event_type, payload, trace_id, span_id, created_at)

-- 上下文快照（压缩/装配结果，用于调试与回放）
context_snapshot(id, step_id, raw_tokens, final_tokens, assembly_plan, created_at)

-- 决策记录（可追溯「为什么这么做」）
decision(id, task_id, decision_type, rationale, context_refs, created_at)

-- 评测
eval_run(id, dataset_version, config, metrics, created_at)
eval_case_result(id, eval_run_id, case_id, passed, score, trace_ref)
```

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 多 Agent 过度设计 | 保留「单 Agent 降级模式」并做对比实验，证明多 Agent 的收益边界 |
| 沙箱安全 | 资源限制 + 网络隔离 + 只读挂载 + 超时强杀 |
| 成本失控 | 预算熔断 + 模型路由 + 缓存 |
| 演示翻车 | 预置 Golden Set 可复现任务 + 录屏备份 |
| 被质疑「套壳」 | 自研编排 + 自研评测 + 自研上下文工程，讲清每个设计取舍 |
