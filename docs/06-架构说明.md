# 架构说明

本文档描述 DevAgent 的运行时架构、数据流与各层契约。
设计取舍的**原因**记录在 [`adr/`](adr/README.md)，本文档聚焦**结构与流向**。

## 2. 分层契约

各层的职责与**允许的依赖方向**（上层依赖下层，反向禁止）：

```
┌─────────────────────────────────────────────────────────────┐
│  CLI / API / Web                                            │  入口层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Orchestration（DAG 调度、失败传播、回退）                    │  编排层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Agents（6 个角色的提示词与输出解析）                         │  Agent 层
└───────┬───────────────────────────────────────────┬─────────┘
        │                                           │
┌───────▼─────────────────┐             ┌───────────▼─────────┐
│  Context Engineering    │             │  Reliability        │
│  （装配/压缩/预算/隔离） │             │  （Reflexion/熔断）  │
└───────┬─────────────────┘             └───────────┬─────────┘
        │                                           │
┌───────▼───────────────────────────────────────────▼─────────┐
│  Model Gateway（唯一模型入口：路由/缓存/记账/降级）            │  模型层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Providers（DeepSeek / Qwen / Zhipu / 任意 OpenAI 兼容）      │
└─────────────────────────────────────────────────────────────┘

横向能力（被各层使用）：
  Observability（Tracing / Metrics）  ·  Tools（Sandbox / CodeIndex）
```

### 硬性规则

| 规则 | 原因 | 如何保证 |
| --- | --- | --- |
| Agent **不得**直接调用 Provider | 绕过网关会丢失记账与降级 | 只传 `ModelGateway` 到 Agent |
| 上下文只能经 `ContextEngine.build()` 构造 | 否则无法量化与审计 | Agent 基类统一走该入口 |
| Verifier 上下文**不含**上游自述 | 防幻觉传播（核心命题） | `ContextIsolator` + 回归测试 |
| 领域模型不可变 | 下游不得偷改上游数据 | `ConfigDict(frozen=True)` |
| 所有模型调用都必须 `charge()` | 否则熔断失效 | 端到端指标可发现遗漏 |

## 3. 上下文工程层详解

### `ContextEngine.build()` 的调用契约

```python
decision = context_engine.build(
    agent_type=AgentType.VERIFIER,
    handoff=handoff,
    candidates=chunks,        # 候选片段（含 relevance/recency/authority 元数据）
    budget=budget,            # 该角色的预算分配
)
```

返回 `AssemblyDecision`，包含：

- `selected`：最终入选的片段（有序，已做位置编排）
- `dropped`：被丢弃的片段及原因（`over_budget` / `duplicate` / `low_score`）
- `tokens_before` / `tokens_after`：压缩前后 token 数
- `compressed`：是否发生压缩（**独立标记**，不由 token 差值推断）

`dropped` 的原因分类很重要：它让「为什么这个信息没进去」可被直接回答，
而不是只能靠推测。

### 装配算法

```
输入: candidates[], budget

1. 计算每个候选的得分
   score = w_rel·relevance + w_rec·recency + w_auth·authority

2. 贪心选择（含硬去重门禁）
   selected = []
   fingerprints = set()
   while budget 允许:
       for chunk in 按 score 降序:
           if chunk.fingerprint in fingerprints: skip    # ← 硬去重
           penalty = w_red · max_similarity(selected) ** 4   # ← 指数惩罚
           effective = chunk.score - penalty
       pick argmax(effective)
       selected.append(pick); fingerprints.add(pick.fingerprint)

3. 位置编排（对抗 lost-in-the-middle）
   高价值片段置于**头部与尾部**，中价值片段居中
```

详见 [ADR-0002](adr/0002-上下文装配使用硬去重作为保险.md)。

### 隔离规则

```python
class ContextIsolator:
    """控制 ContextSpace 之间的访问。

    Verifier 空间的禁止清单：
      - 任何 Coder/Architect 的 output.content（自我解释）
      - 任何 AgentMessage.type == EXPLANATION 的消息

    Verifier 空间允许的内容：
      - 需求规格中的 acceptance_criteria 原文
      - 客观产物（diff、文件内容、测试 stdout）
      - 上一轮的 FeedbackPayload（仅结构化字段）
    """
```

这条边界是**代码强制**的，有专门的契约测试（`test_assembly_contract.py`）。

## 4. 编排层详解

### 节点状态机

```
PENDING ──(依赖就绪)──▶ RUNNING ──┬──▶ SUCCESS
                                   ├──▶ FAILED ──┐
                                   └──▶ (验证驳回)│
                                        │        │
                                        ▼        │
                                   回退重试       │
                                        │        │
                                        └────────┘
                                                  │
                              (上游 FAILED) ──▶ SKIPPED
```

`StepStatus` 取值：`PENDING` / `RUNNING` / `SUCCESS` / `FAILED` / `SKIPPED`。

### 递归失败传播

上游失败时，必须把**所有传递下游**标记为 `SKIPPED`，而不只是一层。
实现是循环扫描至收敛（一个真实 bug 的修复，见 `docs/05`）。

### 回退语义

验证驳回时的动作序列（顺序重要）：

```
1. feedback = FeedbackPayload(failed_criteria, suggestions, lesson)
2. reflexion.record(agent_type, lesson)          # 教训入库
3. checkpoint.clear_step(node_id)                # ★ 作废检查点（关键）
4. 受影响节点重置为 PENDING
5. attempt += 1；超过 max_attempts 则 FAILED
```

第 3 步是必须的：否则重试会读到自己上一轮写入的「已完成」检查点，
直接短路成功，回退机制完全失效（真实 bug，有回归测试守护）。

### 并行执行

无依赖的节点通过 `asyncio.gather` 并行。

> **已知约束**：`asyncio.gather` 为每个子任务创建独立的 context 副本，
> 因此 `contextvars` 的隐式父子栈会断裂。这就是 `Span` 使用**显式 parent 指针**
> 而非 contextvar 的原因（见 [ADR-0003](adr/0003-可观测性不硬绑-opentelemetry.md)）。

## 5. 可靠性机制

| 机制 | 模块 | 作用 |
| --- | --- | --- |
| Reflexion | `reliability/reflexion.py` | 失败教训按 Agent 分桶、FIFO、去重，注入下次尝试 |
| 检查点 | `reliability/checkpoint.py` | 断点续跑；回退时 `clear_step` 作废 |
| 熔断 | `reliability/breaker.py` | token + 步数双阈值，超限中止任务 |
| 循环检测 | `reliability/loop_detector.py` | 尝试次数 + 重复失败签名 + 路径环 |

### 熔断的记账完整性

**所有**模型调用都必须计入预算，包括：

- 需求分析阶段
- 架构设计阶段（通常最贵）
- 缓存命中（token 计 0 但调用计 1）
- 失败调用（token 计 0，但记录延迟与错误）

一个真实 bug 是「需求/架构两个必经阶段完全游离在熔断之外」，
修复后由端到端指标验证覆盖。

## 6. 模型层

### 网关的三条路径

每次 `chat()` 调用归属且仅归属一条路径，**三条都埋点**：

| 路径 | 记账 | 指标 |
| --- | --- | --- |
| 缓存命中 | `cost=0`，`cached=True` | `cached=true` 标签 |
| 调用成功 | 实际 token 与成本 | 正常记录 |
| 调用失败 | `tokens=0`，记录错误与延迟 | `status=error` |

### 供应商降级

`_candidate_specs()` 构造候选列表：首选在前，同档位的其他已启用供应商在后。
降级顺序**与档位绑定**（不是全局固定）——用 `glm-4-plus` 顶替 `qwen-turbo`
是方向错误的降级。

### 语义缓存

当前实现是「规范化消息 + 模型 + 温度」的 SHA256 精确匹配 + LRU。
接口设计允许替换为 embedding 相似度检索版本（`SemanticCache` 的公开方法不变）。

**带工具调用的结果不缓存**（有副作用）。

## 7. API 层

```
POST /api/v1/tasks
  → TaskService.submit()  创建 asyncio Task，立即返回 task_id
  → 后台执行，通过 EventBus 广播事件

GET  /api/v1/tasks/{id}/events   (SSE)
  → 先回放历史事件（晚订阅者也能拿到完整时间线）
  → 再流式推送新事件
  → 15s 心跳保活
  → 任务终态时自动关闭连接
```

### EventBus 的背压策略

订阅者队列满时**丢弃最旧事件**，而不是阻塞发布者。

理由：任务的执行进度不能被一个慢消费者拖住。SSE 客户端断线重连后会
通过历史回放补齐，因此丢事件对最终一致性无损，但对**实时性**有影响——
这是刻意的取舍。

### 事件类型

`task.started` / `node.started` / `node.verdict` / `node.finished` / `task.finished`

## 8. 前端

`web/` 是**零构建**的三栏控制台：

- 左：任务提交 + 任务列表
- 中：SSE 执行时间线（节点状态实时更新）
- 右：上下文工程仪表盘 + 指标

技术选择：原生 ES Module，无 `npm install`，打开 `index.html` 即用。
原因见 README 的常见问题。代价是没有组件化与类型检查，
对这个规模的界面可以接受。

## 9. 扩展点

| 想扩展 | 实现方式 |
| --- | --- |
| 接入新模型供应商 | 实现 `ModelProvider` Protocol，注册到网关 |
| 自定义上下文评分 | 替换 `assembly.py` 中的权重配置 |
| 换裁判模型/策略 | 实现 `JudgeBackend` Protocol |
| 接现有观测平台 | 实现 `SpanExporter` Protocol |
| 强隔离沙箱 | 实现 `Sandbox` Protocol（参考 `DockerSandbox`） |
| 持久化任务 | 实现 `TaskStore` Protocol（当前为内存 LRU） |

所有扩展点都通过 Protocol 定义，**不需要修改框架代码**。
