# 架构说明

本文档描述 DevAgent 的运行时架构、数据流与各层契约。
设计取舍的**原因**记录在 [`adr/`](adr/README.md)，本文档聚焦**结构与流向**。

## 1. 全局数据流

                                         │  constraints, relevant_files)

                          │  ② Architect Agent          │
                          │  技术方案 + DAG 任务分解     │
                          └──────────────┬──────────────┘

        ┌────────────────────────────────────────────────────────────┐
        │  ③ Orchestrator 主循环                                      │
        │  ┌──────────────────────────────────────────────────────┐  │

        │  │     ready = all(dep SUCCESS)                         │  │

## 2. 分层契约

各层的职责与**允许的依赖方向**（上层依赖下层，反向禁止）：

```
┌─────────────────────────────────────────────────────────────┐
│  CLI / API / Web                                            │  入口层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Orchestration（DAG 调度、失败传播、回退）                    │  编排层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Agents（6 个角色的提示词与输出解析）                         │  Agent 层
└───────┬───────────────────────────────────────────┬─────────┘
        │                                           │
┌───────▼─────────────────┐             ┌───────────▼─────────┐
│  Context Engineering    │             │  Reliability        │
│  （装配/压缩/预算/隔离） │             │  （Reflexion/熔断）  │
└───────┬─────────────────┘             └───────────┬─────────┘
        │                                           │
┌───────▼───────────────────────────────────────────▼─────────┐
│  Model Gateway（唯一模型入口：路由/缓存/记账/降级）            │  模型层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Providers（DeepSeek / Qwen / Zhipu / 任意 OpenAI 兼容）      │
└─────────────────────────────────────────────────────────────┘

横向能力（被各层使用）：
  Observability（Tracing / Metrics）  ·  Tools（Sandbox / CodeIndex）
```

### 硬性规则

| 规则 | 原因 | 如何保证 |
| --- | --- | --- |
| Agent **不得**直接调用 Provider | 绕过网关会丢失记账与降级 | 只传 `ModelGateway` 到 Agent |
| 上下文只能经 `ContextEngine.build()` 构造 | 否则无法量化与审计 | Agent 基类统一走该入口 |
| Verifier 上下文**不含**上游自述 | 防幻觉传播（核心命题） | `ContextIsolator` + 回归测试 |
| 领域模型不可变 | 下游不得偷改上游数据 | `ConfigDict(frozen=True)` |
| 所有模型调用都必须 `charge()` | 否则熔断失效 | 端到端指标可发现遗漏 |

## 3. 上下文工程层详解

### `ContextEngine.build()` 的调用契约

```python
decision = context_engine.build(
    agent_type=AgentType.VERIFIER,
    handoff=handoff,
    candidates=chunks,        # 候选片段（含 relevance/recency/authority 元数据）
    budget=budget,            # 该角色的预算分配
)
```

返回 `AssemblyDecision`，包含：

- `selected`：最终入选的片段（有序，已做位置编排）
- `dropped`：被丢弃的片段及原因（`over_budget` / `duplicate` / `low_score`）
- `tokens_before` / `tokens_after`：压缩前后 token 数
- `compressed`：是否发生压缩（**独立标记**，不由 token 差值推断）

`dropped` 的原因分类很重要：它让「为什么这个信息没进去」可被直接回答，
而不是只能靠推测。

### 装配算法

```
输入: candidates[], budget

1. 计算每个候选的得分
   score = w_rel·relevance + w_rec·recency + w_auth·authority

2. 贪心选择（含硬去重门禁）
   selected = []
   fingerprints = set()
   while budget 允许:
       for chunk in 按 score 降序:
           if chunk.fingerprint in fingerprints: skip    # ← 硬去重
           penalty = w_red · max_similarity(selected) ** 4   # ← 指数惩罚
           effective = chunk.score - penalty
       pick argmax(effective)
       selected.append(pick); fingerprints.add(pick.fingerprint)

3. 位置编排（对抗 lost-in-the-middle）
   高价值片段置于**头部与尾部**，中价值片段居中
```

详见 [ADR-0002](adr/0002-上下文装配使用硬去重作为保险.md)。

### 隔离规则

```python
class ContextIsolator:
    """控制 ContextSpace 之间的访问。

    Verifier 空间的禁止清单：
      - 任何 Coder/Architect 的 output.content（自我解释）
      - 任何 AgentMessage.type == EXPLANATION 的消息

    Verifier 空间允许的内容：
      - 需求规格中的 acceptance_criteria 原文
      - 客观产物（diff、文件内容、测试 stdout）
      - 上一轮的 FeedbackPayload（仅结构化字段）
    """
```

这条边界是**代码强制**的，有专门的契约测试（`test_assembly_contract.py`）。

## 4. 编排层详解

### 节点状态机

```
PENDING ──(依赖就绪)──▶ RUNNING ──┬──▶ SUCCESS
                                   ├──▶ FAILED ──┐
                                   └──▶ (验证驳回)│
                                        │        │
                                        ▼        │
                                   回退重试       │
                                        │        │
                                        └────────┘
                                                  │
                              (上游 FAILED) ──▶ SKIPPED
```

`StepStatus` 取值：`PENDING` / `RUNNING` / `SUCCESS` / `FAILED` / `SKIPPED`。

### 递归失败传播

上游失败时，必须把**所有传递下游**标记为 `SKIPPED`，而不只是一层。
实现是循环扫描至收敛（一个真实 bug 的修复，见 `docs/05`）。

### 回退语义

验证驳回时的动作序列（顺序重要）：

```
1. feedback = FeedbackPayload(failed_criteria, suggestions, lesson)
2. reflexion.record(agent_type, lesson)          # 教训入库
3. checkpoint.clear_step(node_id)                # ★ 作废检查点（关键）
4. 受影响节点重置为 PENDING
5. attempt += 1；超过 max_attempts 则 FAILED
```

第 3 步是必须的：否则重试会读到自己上一轮写入的「已完成」检查点，
直接短路成功，回退机制完全失效（真实 bug，有回归测试守护）。

### 并行执行

无依赖的节点通过 `asyncio.gather` 并行。

> **已知约束**：`asyncio.gather` 为每个子任务创建独立的 context 副本，
> 因此 `contextvars` 的隐式父子栈会断裂。这就是 `Span` 使用**显式 parent 指针**
> 而非 contextvar 的原因（见 [ADR-0003](adr/0003-可观测性不硬绑-opentelemetry.md)）。

## 5. 可靠性机制

| 机制 | 模块 | 作用 |
| --- | --- | --- |
| Reflexion | `reliability/reflexion.py` | 失败教训按 Agent 分桶、FIFO、去重，注入下次尝试 |
| 检查点 | `reliability/checkpoint.py` | 断点续跑；回退时 `clear_step` 作废 |
| 熔断 | `reliability/breaker.py` | token + 步数双阈值，超限中止任务 |
| 循环检测 | `reliability/loop_detector.py` | 尝试次数 + 重复失败签名 + 路径环 |

### 熔断的记账完整性

**所有**模型调用都必须计入预算，包括：

- 需求分析阶段
- 架构设计阶段（通常最贵）
- 缓存命中（token 计 0 但调用计 1）
- 失败调用（token 计 0，但记录延迟与错误）

一个真实 bug 是「需求/架构两个必经阶段完全游离在熔断之外」，
修复后由端到端指标验证覆盖。

## 6. 模型层

### 网关的三条路径

每次 `chat()` 调用归属且仅归属一条路径，**三条都埋点**：

| 路径 | 记账 | 指标 |
| --- | --- | --- |
| 缓存命中 | `cost=0`，`cached=True` | `cached=true` 标签 |
| 调用成功 | 实际 token 与成本 | 正常记录 |
| 调用失败 | `tokens=0`，记录错误与延迟 | `status=error` |

### 供应商降级

`_candidate_specs()` 构造候选列表：首选在前，同档位的其他已启用供应商在后。
降级顺序**与档位绑定**（不是全局固定）——用 `glm-4-plus` 顶替 `qwen-turbo`
是方向错误的降级。

### 语义缓存

两种实现，通过 `DEVAGENT_CACHE__SEMANTIC` 选择：

```
ModelGateway ──→ SemanticCache          精确匹配（默认）
              └─→ VectorSemanticCache   精确短路 + 向量近邻

_cache_get / _cache_put  ← 适配同步/异步两种签名
```

| | 精确匹配 | 向量检索 |
| --- | --- | --- |
| 判定 | 全消息 SHA-256 相同 | 余弦相似度 ≥ 阈值 |
| 额外调用 | 无 | 每次未命中多一次嵌入 |
| 依赖 | 无 | 嵌入模型（默认 qwen text-embedding-v3） |
| 能否命中「措辞不同」 | 否 | 是 |

**两级顺序不能反**：先精确后近似。精确匹配是零成本的字典查找，
放在前面避免对已确定的请求白算一次嵌入（有专门测试守护）。

**只嵌入最后一条消息**：拼接历史会让所有请求的向量向"平均语义"塌缩，
两个不同需求因为共享同样的长系统提示而变得"相似"。

**按 `(model, temperature)` 分桶**：跨模型召回会返回
"看起来相似但来自别的模型"的结果 —— 在需要模型可复现性的场景里
是**正确的灾难**。可用 `model_filter=false` 关闭，但默认开启。

**嵌入失败自动降级**为精确匹配。缓存是**优化**而非**功能** ——
这是本模块最重要的不变量，有专门测试覆盖。

**为什么不用 ANN（FAISS/hnswlib）**：512 条 × 1024 维的线性扫描约 0.5ms，
相比一次模型调用（数百毫秒）可忽略。ANN 是**近似**的（可能漏掉真最近邻），
引入它等于用非确定性 + 重依赖换一个当前不存在的性能问题。
条目数超过 10⁴ 时再改造成可插拔的 `VectorIndex` 协议。

**带工具调用的结果不缓存**（有副作用）。两种实现都遵守这一条。

度量升级是否有效的唯一依据是 `GET /api/v1/cache` 的
`semantic_hits` / `semantic_share` —— 若语义命中长期为 0，
说明该场景请求差异本就大，应关掉以免白付嵌入成本。

### 异构裁判与偏差标定

LLM-as-Judge 的偏差分三层，需要三个不同机制，缺一层就有一类偏差漏网：

| 偏差 | 机制 | 在哪一层 |
| --- | --- | --- |
| 位置偏差（候选在前/在后分数不同） | 双向评估 + 交换位置 | `LLMJudge`（ADR-0005） |
| 单次采样噪声 | 两次采样取平均 + `inconsistent` 标记 | `LLMJudge` |
| **自我偏好**（给同族输出打分偏高） | **异构参考裁判 + 偏差标定** | `JudgePanel`（ADR-0008） |

```
JudgePanel
  ├─ primary     主裁判（产出实际评分）
  ├─ reference   异构参考裁判（仅用于标定，可选）
  └─ calibration CalibrationResult（bias / relative_bias / trustworth）
```

**异构判定按模型族，而非模型名**：

```
deepseek-chat / deepseek-reasoner / deepseek-coder → family: deepseek
qwen-plus / qwen-max / qwen-turbo                 → family: qwen
glm-4 / glm-4-plus                                → family: zhipu
```

`deepseek-chat` 与 `deepseek-reasoner` 名字不同但**同族**。把同族误判为异构，
是让"异构裁判"沦为自欺欺人的唯一方式，因此有专门测试守护。

三种情形处理方式**刻意不同**：

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 主裁判异构 | 直接用，标 `judge_relation=heterogeneous` | 无需校正，省算力 |
| 同源 + 已标定 | 按 `bias` 扣减，**并用主裁判阈值重算 `passed`** | 有依据的校正 |
| 同源 + 无标定 | **如实返回**，标 `uncalibrated_self_preference=true` | 见下 |

第三种的取舍是本模块最重要的判断：**用未经验证的常数扣分，比不扣分更糟。**
未被修正的高分读者会警惕，被"修正"过的高分读者会信任 —— 若常数是拍脑袋来的，
你只是把可疑数字包装成了可信数字。

**标定必须在 `JudgeResult` 层完成，不能放到报告层**：`passed` 由 `overall`
与阈值比较得出，只改 `overall` 不改 `passed` 会产生「2.8 分但 passed=True」
的自相矛盾结果。`_apply_calibration()` 因此把两件事原子地一起做。

**标定探针用真实 golden set 的验收标准文本**，而非人造样本：
人造样本天然偏"干净"，裁判在其上的偏差与在真实输出上的偏差不是同一个数。
用验收标准文本本身作候选输出，内容中性但分布一致。

**可靠性门槛 `_MIN_CALIBRATION_SAMPLES = 20`**：偏差是均量，标准误 ≈ `sigma/√n`。
取 `sigma≈0.8`（1-5 分制裁判分数的典型标准差），要让标准误降到 0.2 需 `n≈16`，
取 20 留余量。低于门槛则 `trustworth=False`，**不用于校正**。

标定结果写进 `EvalReport.calibration` 并出现在 `summary()` 里 ——
`mean_judge_score` 是否被校正过，直接决定读者怎么解读这个数字。

## 7. API 层

```
POST /api/v1/tasks
  → TaskService.submit()  创建 asyncio Task，立即返回 task_id
  → 后台执行，通过 EventBus 广播事件

GET  /api/v1/tasks/{id}/events   (SSE)
  → 先回放历史事件（晚订阅者也能拿到完整时间线）
  → 再流式推送新事件
  → 15s 心跳保活
  → 任务终态时自动关闭连接
```

### EventBus 的背压策略

订阅者队列满时**丢弃最旧事件**，而不是阻塞发布者。

理由：任务的执行进度不能被一个慢消费者拖住。SSE 客户端断线重连后会
通过历史回放补齐，因此丢事件对最终一致性无损，但对**实时性**有影响——
这是刻意的取舍。

### 事件类型

`task.started` / `node.started` / `node.verdict` / `node.finished` / `task.finished`

### 存储层（`TaskStore` 协议）

API 层只依赖 `TaskStore` 协议，**不感知**底层是内存还是数据库：

```
TaskService ──→ TaskStore（Protocol）
                  ├─ InMemoryTaskStore   同步，零依赖，进程内 LRU
                  └─ SqlTaskStore        异步，持久化，跨重启
```

**为什么协议不声明 `async`**：内存实现是纯同步的，强行加 `async def` 会让
纯逻辑单测集体被迫变成协程，并为每次调用引入协程调度开销。异步的 SQL 实现
由一个极薄的适配器 `_maybe_await(value)` 承载 —— 是 awaitable 就 await，
否则直接返回。一次 `isawaitable` 判断（纳秒级）换来两种实现共用同一套调用代码。

**事件也必须落库**：内存 `EventBus` 的历史缓冲随进程消失。任务可能跑几分钟，
用户晚半小时才打开页面，或服务正好重启 —— 此时 SSE 的历史回放必须仍然有效。
`TaskEventRow` 的 `seq` 在任务内单调递增，天然去重且支持断点续拉。

**类型收窄集中在边界**：`_maybe_await` 的返回类型只能是 `Any`（入参既可能是
协程也可能是普通值）。若在每个调用点各自 `cast`，问题只是被藏起来；因此统一
经 `_as_dict` / `_as_dict_list` 收窄一次，调用点保持干净，mypy strict 也能过。

**刻意不做的两件事**：

1. **不自动清理历史任务** —— 保留期是运维策略而非应用逻辑。硬编码 TTL 会让
   需要长期留存审计记录的部署很难受，因此只提供 `delete`，策略留给外部。
2. **不共用领域模型与 ORM 模型** —— 领域模型是 `frozen` + `extra="forbid"`
   （服务于 Agent 间强类型握手），与 ORM 的可变映射冲突；且存储结构是为查询
   设计的，与 Agent 视角的数据形状不同。两者边界是 `_row_to_dict` 一处转换点。

## 8. 前端

`web/` 是**零构建**的三栏控制台：

- 左：任务提交 + 任务列表
- 中：SSE 执行时间线（节点状态实时更新）
- 右：上下文工程仪表盘 + 指标

技术选择：原生 ES Module，无 `npm install`，打开 `index.html` 即用。
原因见 README 的常见问题。代价是没有组件化与类型检查，
对这个规模的界面可以接受。

| 接现有观测平台 | 实现 `SpanExporter` Protocol |
| 强隔离沙箱 | 实现 `Sandbox` Protocol（参考 `DockerSandbox`） |
| 持久化任务 | 实现 `TaskStore` Protocol（内存 / SQL 两种实现已就绪，ADR-0006） |
| 换向量检索算法 | 替换 `VectorSemanticCache` 的线性扫描（≥10⁴ 条时再考虑 ANN，ADR-0007） |

所有扩展点都通过 Protocol 定义，**不需要修改框架代码**。
