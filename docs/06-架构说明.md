# 架构说明

本文档描述 DevAgent 的运行时架构、数据流与各层契约。
代码产物尚未应用到测试工作区，检查点默认只保存在进程内；能力边界与质量记录见 [质量与已知限制](07-质量与已知限制.md)。
设计取舍的**原因**记录在 [`adr/`](adr/README.md)，本文档聚焦**结构与流向**。

## 2. 分层契约

各层的职责与**允许的依赖方向**（上层依赖下层，反向禁止）：

```
┌─────────────────────────────────────────────────────────────┐
│  CLI / API / Web                                            │  入口层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Orchestration（DAG 调度、失败传播、回退）                    │  编排层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Agents（6 个角色的提示词与输出解析）                         │  Agent 层
└───────┬───────────────────────────────────────────┬─────────┘
        │                                           │
┌───────▼─────────────────┐             ┌───────────▼─────────┐
│  Context Engineering    │             │  Reliability        │
│  （装配/压缩/预算/隔离） │             │  （Reflexion/熔断）  │
└───────┬─────────────────┘             └───────────┬─────────┘
        │                                           │
┌───────▼───────────────────────────────────────────▼─────────┐
│  Model Gateway（唯一模型入口：路由/缓存/记账/降级）            │  模型层
└───────────────────────────┬─────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────┐
│  Providers（DeepSeek / Qwen / Zhipu / 任意 OpenAI 兼容）      │
└─────────────────────────────────────────────────────────────┘

横向能力（被各层使用）：
  Observability（Tracing / Metrics）  ·  Tools（Sandbox / CodeIndex）
```

### 硬性规则

| 规则 | 原因 | 如何保证 |
| --- | --- | --- |
| Agent **不得**直接调用 Provider | 绕过网关会丢失记账与降级 | 只传 `ModelGateway` 到 Agent |
| 上下文只能经 `ContextEngine.build()` 构造 | 否则无法量化与审计 | Agent 基类统一走该入口 |
| Verifier 上下文**不含**上游自述 | 防幻觉传播（核心命题） | `ContextIsolator` + 回归测试 |
| 领域模型不可变 | 下游不得偷改上游数据 | `ConfigDict(frozen=True)` |
| 所有模型调用都必须 `charge()` | 否则熔断失效 | 端到端指标可发现遗漏 |

## 3. 上下文工程层详解

### `ContextEngine.build()` 的调用契约

```python
decision = context_engine.build(
    agent_type=AgentType.VERIFIER,
    handoff=handoff,
    candidates=chunks,        # 候选片段（含 relevance/recency/trust 等打分元数据）
    budget=budget,            # 该角色的预算分配
)
```

返回 `AssemblyDecision`，包含：

- `selected`：最终入选的片段（有序，已做位置编排）
- `dropped`：被丢弃的片段及原因（`over_budget` / `duplicate` / `low_score`）
- `tokens_before` / `tokens_after`：压缩前后 token 数
- `compressed`：是否发生压缩（**独立标记**，不由 token 差值推断）

`dropped` 的原因分类很重要：它让「为什么这个信息没进去」可被直接回答，
而不是只能靠推测。

### 装配算法

```
输入: candidates[], budget

1. 计算每个候选的得分
   score = w_rel·relevance + w_rec·recency + w_dep·dependency
         + w_den·density + w_trust·trust - w_red·redundancy

2. 贪心选择（含硬去重门禁）
   selected = []
   fingerprints = set()
   while budget 允许:
       for chunk in 按 score 降序:
           if chunk.fingerprint in fingerprints: skip    # ← 硬去重
           penalty = w_red · max_similarity(selected) ** 4   # ← 指数惩罚
           effective = chunk.score - penalty
       pick argmax(effective)
       selected.append(pick); fingerprints.add(pick.fingerprint)

3. 位置编排（对抗 lost-in-the-middle）
   高价值片段置于**头部与尾部**，中价值片段居中
```

详见 [ADR-0002](adr/0002-上下文装配使用硬去重作为保险.md)。

### 内容信任度与注入防护

上下文片段按**来源**分级信任度（与内容长什么样无关）：

| 等级 | 来源 scheme | 处置 | 装配权重 |
| --- | --- | --- | --- |
| SYSTEM | `system://` `handoff://` | 原样注入 | 1.0 |
| USER | `user://` | 原样注入 | 1.0 |
| WORKSPACE | `step://` `artifact://` `verify://` | 加边界 | 1.0 |
| EXTERNAL | `file://` `web://` `tool://` `sandbox://` | 加边界 + 低可信警告 | 0.25 |
| UNKNOWN | 未登记或缺失 | 同上 | 0.0625 |

未登记的 scheme 一律落到 UNKNOWN —— **保守默认**：新代码路径忘记登记时
应当偏保守，而不是"看起来还行"。

渲染时不可信内容被随机 nonce 定界：

```
<EXTERNAL_NONCE_6741fa0aeca38025>
……原始内容原样保留……
</EXTERNAL_NONCE_6741fa0aeca38025>
```

**三个必须记住的点**：

1. **nonce 必须随机**。固定定界符（`<untrusted>`）下攻击者只要写上
   闭合标签就能越狱 —— 随机 nonce 让这种逃逸在密码学上不可行。
2. **权重必须单侧**（`0.25 ** max(0, WORKSPACE - level)`）。
   对称公式会让 SYSTEM(4) 算出 0.0625 **低于**外部内容的 0.25 ——
   防护机制反过来把系统约束挤出上下文。这个 bug 真实发生过，
   现由 `test_system_outranks_external` 守护。
3. **打分与边界是两个正交防线**。打分决定"选不选"（防止恶意长文件
   挤掉合法内容），边界决定"选了之后模型怎么看待它"。缺一不可。

**为什么不做内容检测/黑名单**：攻击面是自然语言的全部空间
（多语言、编码、同形字、零宽字符），黑名单永远漏；而源码里合法出现
"ignore all previous" 的场景真实存在（写注入检测器的项目就是），
误删会让 Agent 收到不完整上下文、产出无法归因的错误。
防护依赖**来源的可枚举性**，而非**内容模式的可枚举性**。

有一个测试直接断言启发式检测函数**不出现在**渲染路径的源码里
（`test_not_used_in_production_render_path`）—— 把"拒绝黑名单"
从文档承诺变成可执行约束。

**零影响承诺**：SYSTEM / USER / WORKSPACE 权重全为 1.0，
开启防护后内部来源片段的打分逐位不变，由信任度与装配契约测试约束；当前全量验证结果见 [质量文档](07-质量与已知限制.md)。

详见 [ADR-0009](adr/0009-提示词注入信任度分级.md)。

### 隔离规则

```python
class ContextIsolator:
    """控制 ContextSpace 之间的访问。

    Verifier 空间的禁止清单：
      - 任何 Coder/Architect 的 output.content（自我解释）
      - 任何 AgentMessage.type == EXPLANATION 的消息

    Verifier 空间允许的内容：
      - 需求规格中的 acceptance_criteria 原文
      - 客观产物（diff、文件内容、测试 stdout）
      - 上一轮的 FeedbackPayload（仅结构化字段）
    """
```

编排器从结构化 changes 提取路径与 diff，排除 summary、reason 与作者的效果声明。实际模型输入由 `tests/integration/test_orchestrator.py` 检查。

## 4. 编排层详解

### 节点状态机

```
PENDING ──(依赖就绪)──▶ RUNNING ──┬──▶ SUCCESS
                                   ├──▶ FAILED ──┐
                                   └──▶ (验证驳回)│
                                        │        │
                                        ▼        │
                                   回退重试       │
                                        │        │
                                        └────────┘
                                                  │
                              (上游 FAILED) ──▶ SKIPPED
```

`StepStatus` 还包含 READY / VERIFYING / REJECTED；当前调度路径实际标记 PENDING / RUNNING / SUCCESS / FAILED / SKIPPED，前端契约覆盖整个枚举。

### 递归失败传播

上游失败时，必须把**所有传递下游**标记为 `SKIPPED`，而不只是一层。
实现是循环扫描至收敛，回归用例覆盖多层失败传播。

### 回退语义

验证驳回时的动作序列（顺序重要）：

```
1. feedback = FeedbackPayload(failed_criteria, suggestions, lesson)
2. reflexion.record(agent_type, lesson)          # 教训入库
3. checkpoint.clear_step(node_id)                # 作废检查点（双保险）
4. reset_subgraph(node_id) → 受影响节点重置为 PENDING，并清掉它们的检查点
5. attempt += 1；超过 max_retries / 相同失败重复 N 次 / 回退成环 则 FAILED
```

**检查点只在验证通过后才写入**（`_save_checkpoint` 位于 `Verdict.PASS` 分支）。
这是第 3 步之外的第二道保险：早先的实现在**验证之前**就写
`completed=True`，于是被驳回、甚至重试耗尽的节点也留下"已完成"记录 ——
同一个 `task_id` 再跑一次就会被短路，一步不执行却报成功（真实 bug）。

第 3 步仍然保留：回退只是"作废重跑"的一种触发方式，把它写死在回退路径上，
即使将来新增别的回退入口也不会漏掉。

### 并行执行

无依赖的节点通过 `asyncio.gather` 并行。每个节点、Tester 与 Verifier 使用独立上下文快照；节点产物按 id 存储，依赖节点的路径与代码显式进入下游输入。检查点同时保存产物，恢复时还原到运行状态。

测试运行时的配置目录只提供基线。每次调用在独立目录中复制基线、写入测试并执行，结束或取消后清理；并发任务不共享生成文件。

> **已知约束**：`asyncio.gather` 为每个子任务创建独立的 context 副本，
> 因此 `contextvars` 的隐式父子栈会断裂。这就是 `Span` 使用**显式 parent 指针**
> 而非 contextvar 的原因（见 [ADR-0003](adr/0003-可观测性不硬绑-opentelemetry.md)）。

## 5. 可靠性机制

| 机制 | 模块 | 作用 |
| --- | --- | --- |
| Reflexion | `reliability/reflexion.py` | 失败教训按 Agent 分桶、FIFO、去重，注入下次尝试 |
| 检查点 | `reliability/checkpoint.py` | 断点续跑；回退时 `clear_step` 作废 |
| 熔断 | `reliability/breaker.py` | token + 步数双阈值，超限中止任务 |
| 循环检测 | `reliability/loop_detector.py` | 尝试次数 + 重复失败签名 + 路径环 |

### 熔断的记账完整性

**所有**模型调用都必须计入预算，包括：

- 需求分析阶段
- 架构设计阶段（通常最贵）
- 缓存命中（服务出去的 token 计入预算，费用记为 0）
- 失败调用（获得模型响应后解析失败也按真实 token 与费用计账；无 usage 的网络失败记录错误）

一个真实 bug 是「需求/架构两个必经阶段完全游离在熔断之外」，
修复后由端到端指标验证覆盖。

## 6. 模型层

### 网关的三条路径

每次 `chat()` 调用归属且仅归属一条路径，**三条都埋点**：

| 路径 | 记账 | 指标 |
| --- | --- | --- |
| 缓存命中 | `cost=0`，`cached=True` | `cached=true` 标签 |
| 调用成功 | 实际 token 与成本 | 正常记录 |
| 调用失败 | `tokens=0`，记录错误与延迟 | `status=error` |

### 供应商降级

`_candidate_specs()` 构造候选列表：首选在前，同档位的其他已启用供应商在后。
降级顺序**与档位绑定**（不是全局固定）——用 `glm-4-plus` 顶替 `qwen-turbo`
是方向错误的降级。

### 语义缓存

两种实现，通过 `DEVAGENT_CACHE__SEMANTIC` 选择：

```
ModelGateway ──→ SemanticCache          精确匹配（默认）
              └─→ VectorSemanticCache   精确短路 + 向量近邻

_cache_get / _cache_put  ← 适配同步/异步两种签名
```

| | 精确匹配 | 向量检索 |
| --- | --- | --- |
| 判定 | 全消息 SHA-256 相同 | 余弦相似度 ≥ 阈值 |
| 额外调用 | 无 | 每次未命中多一次嵌入 |
| 依赖 | 无 | 嵌入模型（默认 qwen text-embedding-v3） |
| 能否命中「措辞不同」 | 否 | 是 |

**两级顺序不能反**：先精确后近似。精确匹配是零成本的字典查找，
放在前面避免对已确定的请求白算一次嵌入（有专门测试守护）。

**只嵌入最后一条消息**：拼接历史会让所有请求的向量向"平均语义"塌缩，
两个不同需求因为共享同样的长系统提示而变得"相似"。

**按 `(model, temperature)` 分桶**：跨模型召回会返回
"看起来相似但来自别的模型"的结果 —— 在需要模型可复现性的场景里
是**正确的灾难**。可用 `model_filter=false` 关闭，但默认开启。

**嵌入失败自动降级**为精确匹配。缓存是**优化**而非**功能** ——
这是本模块最重要的不变量，有专门测试覆盖。

**为什么不用 ANN（FAISS/hnswlib）**：512 条 × 1024 维的线性扫描约 0.5ms，
相比一次模型调用（数百毫秒）可忽略。ANN 是**近似**的（可能漏掉真最近邻），
引入它等于用非确定性 + 重依赖换一个当前不存在的性能问题。
条目数超过 10⁴ 时再改造成可插拔的 `VectorIndex` 协议。

**带工具调用的结果不缓存**（有副作用）。两种实现都遵守这一条。

度量升级是否有效的唯一依据是 `GET /api/v1/cache` 的
`semantic_hits` / `semantic_share` —— 若语义命中长期为 0，
说明该场景请求差异本就大，应关掉以免白付嵌入成本。

### 异构裁判与偏差标定

LLM-as-Judge 的偏差分三层，需要三个不同机制，缺一层就有一类偏差漏网：

| 偏差 | 机制 | 在哪一层 |
| --- | --- | --- |
| 位置偏差（候选在前/在后分数不同） | 双向评估 + 交换位置 | `LLMJudge`（ADR-0005） |
| 单次采样噪声 | 两次采样取平均 + `inconsistent` 标记 | `LLMJudge` |
| **自我偏好**（给同族输出打分偏高） | **异构参考裁判 + 偏差标定** | `JudgePanel`（ADR-0008） |

```
JudgePanel
  ├─ primary     主裁判（产出实际评分）
  ├─ reference   异构参考裁判（仅用于标定，可选）
  └─ calibration CalibrationResult（bias / relative_bias / trustworth）
```

**异构判定按模型族，而非模型名**：

```
deepseek-chat / deepseek-reasoner / deepseek-coder → family: deepseek
qwen-plus / qwen-max / qwen-turbo                 → family: qwen
glm-4 / glm-4-plus                                → family: zhipu
```

`deepseek-chat` 与 `deepseek-reasoner` 名字不同但**同族**。把同族误判为异构，
是让"异构裁判"沦为自欺欺人的唯一方式，因此有专门测试守护。

三种情形处理方式**刻意不同**：

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 主裁判异构 | 直接用，标 `judge_relation=heterogeneous` | 无需校正，省算力 |
| 同源 + 已标定 | 按 `bias` 扣减，**并用主裁判阈值重算 `passed`** | 有依据的校正 |
| 同源 + 无标定 | **如实返回**，标 `uncalibrated_self_preference=true` | 见下 |

第三种的取舍是本模块最重要的判断：**用未经验证的常数扣分，比不扣分更糟。**
未被修正的高分读者会警惕，被"修正"过的高分读者会信任 —— 若常数是拍脑袋来的，
你只是把可疑数字包装成了可信数字。

**标定必须在 `JudgeResult` 层完成，不能放到报告层**：`passed` 由 `overall`
与阈值比较得出，只改 `overall` 不改 `passed` 会产生「2.8 分但 passed=True」
的自相矛盾结果。`_apply_calibration()` 因此把两件事原子地一起做。

**标定探针用真实 golden set 的验收标准文本**，而非人造样本：
人造样本天然偏"干净"，裁判在其上的偏差与在真实输出上的偏差不是同一个数。
用验收标准文本本身作候选输出，内容中性但分布一致。

**可靠性门槛 `_MIN_CALIBRATION_SAMPLES = 20`**：偏差是均量，标准误 ≈ `sigma/√n`。
取 `sigma≈0.8`（1-5 分制裁判分数的典型标准差），要让标准误降到 0.2 需 `n≈16`，
取 20 留余量。低于门槛则 `trustworth=False`，**不用于校正**。

标定结果写进 `EvalReport.calibration` 并出现在 `summary()` 里 ——
`mean_judge_score` 是否被校正过，直接决定读者怎么解读这个数字。

## 7. API 层

```
POST /api/v1/tasks
  → TaskService.submit()  创建 asyncio Task，立即返回 task_id
  → 后台执行，通过 EventBus 广播事件

GET  /api/v1/tasks/{id}/events   (SSE)
  → 先回放历史事件（晚订阅者也能拿到完整时间线）
  → 再流式推送新事件
  → 15s 心跳保活
  → 任务终态时自动关闭连接
```

### EventBus 的背压策略

订阅者队列满时**丢弃最旧事件**，而不是阻塞发布者。

理由：任务的执行进度不能被一个慢消费者拖住。SSE 客户端断线重连后会
通过历史回放补齐，因此丢事件对最终一致性无损，但对**实时性**有影响——
这是刻意的取舍。

### 事件类型

`task_started` / `node_started` / `node_verdict` / `node_finished` / `task_finished`

（注意是**下划线**而非点号 —— SSE 的 `event:` 字段直接使用这个字面量，
前端按名注册监听器，写错一个字符就静默收不到事件。历史上本文档曾误写为
`task.started` 形式，已修正。）

### 存储层（`TaskStore` 协议）

API 层只依赖 `TaskStore` 协议，**不感知**底层是内存还是数据库：

```
TaskService ──→ TaskStore（Protocol）
                  ├─ InMemoryTaskStore   同步，零依赖，进程内 LRU
                  └─ SqlTaskStore        异步，持久化，跨重启
```

**为什么协议不声明 `async`**：内存实现是纯同步的，强行加 `async def` 会让
纯逻辑单测集体被迫变成协程，并为每次调用引入协程调度开销。异步的 SQL 实现
由一个极薄的适配器 `_maybe_await(value)` 承载 —— 是 awaitable 就 await，
否则直接返回。一次 `isawaitable` 判断（纳秒级）换来两种实现共用同一套调用代码。

**事件也必须落库**：内存 `EventBus` 的历史缓冲随进程消失。任务可能跑几分钟，
用户晚半小时才打开页面，或服务正好重启 —— 此时 SSE 的历史回放必须仍然有效。
`TaskEventRow` 的 `seq` 在任务内单调递增，天然去重且支持断点续拉。

**类型收窄集中在边界**：`_maybe_await` 的返回类型只能是 `Any`（入参既可能是
协程也可能是普通值）。若在每个调用点各自 `cast`，问题只是被藏起来；因此统一
经 `_as_dict` / `_as_dict_list` 收窄一次，调用点保持干净，mypy strict 也能过。

**刻意不做的两件事**：

1. **不自动清理历史任务** —— 保留期是运维策略而非应用逻辑。硬编码 TTL 会让
   需要长期留存审计记录的部署很难受，因此只提供 `delete`，策略留给外部。
2. **不共用领域模型与 ORM 模型** —— 领域模型是 `frozen` + `extra="forbid"`
   （服务于 Agent 间强类型握手），与 ORM 的可变映射冲突；且存储结构是为查询
   设计的，与 Agent 视角的数据形状不同。两者边界是 `_row_to_dict` 一处转换点。

## 8. 前端

`web/` 是**零构建**的多页控制台（6 个路由页），技术选择为原生 ES Module：
无 `npm install`、无打包步骤，`python -m http.server` 或直接打开 `index.html`
即可运行。原因见 README 的常见问题。

代价是没有框架的组件复用，用**自研组件层 + 设计令牌**补上：

### 目录结构

```
web/
├── index.html              外壳挂载点 + 防 FOUC 的主题预置脚本
├── css/
│   ├── tokens.css          设计令牌唯一来源（palette → semantic → 组件层）
│   ├── base.css            reset、排版、焦点策略、打印样式
│   ├── components.css      组件库（按钮/表单/卡片/表格/反馈/浮层/DAG 画布…）
│   ├── responsive.css      通用断点、横屏与强制色覆盖
│   └── workspace.css       工作台布局、任务记录与执行会话的响应式样式
├── js/
│   ├── icons.js            内联 SVG，继承 currentColor
│   ├── util.js             DOM 助手、格式化、指标解析、焦点管理
│   ├── api.js              带超时/取消的 API 客户端 + SSE 订阅
│   ├── store.js            字段级订阅 store + hash 路由
│   ├── backend-settings.js 按后端 schema 渲染全部配置与供应商编辑器
│   ├── task-view.js        任务筛选、最新尝试、验证结论与状态摘要纯函数
│   ├── components.js       组件构造函数（返回 DOM 节点，非 HTML 字符串）
│   ├── shell.js            外壳：主题、侧栏、顶栏、路由渲染、页面生命周期
│   ├── main.js             组装与全局兜底
│   └── pages/              6 个业务页面
├── graph.js                DAG 布局纯函数（不碰 document）
├── graph.test.js           布局与解析回归
├── format.test.js          指标解析与路由回归
└── workspace.test.js       任务筛选、重试产物与验证结论回归
```

### 三条关键设计决策

1. **设计令牌三层架构**。`palette`（原始色值）→ `semantic`（按用途命名，
   如 `--surface-base` / `--text-primary` / `--status-danger`）→ 组件令牌。
   **组件只允许引用语义层**，因此切换明暗主题时组件 CSS 一行都不用改 ——
   这是「暗色模式下图标不变色」这类经典 bug 的结构性解法。
   `make web-check` 校验令牌引用，避免悬空变量。

2. **指标解析集中在一处**。后端 OTLP 指标的真实命名**没有** `devagent_`
   前缀，且直方图是三层嵌套（名称 → 标签 → 统计量）。`util.js` 的
   `metric / histOverallMean / histMaxQuantile` 是唯一翻译层，用后缀匹配
   兜住命名差异，并按 `count` 加权聚合跨标签数据。这类错误不会让页面崩溃，
   只会**静默显示错误结论**，因此由 `format.test.js` 专门钉死。

3. **组件构造函数返回 DOM 节点而非 HTML 字符串**。只有 `icon()` 返回
   SVG 字符串（内容是静态的，无注入面）。用户数据一律走 `textContent`，
   这是本项目的 XSS 基线。

### 任务工作区

默认入口为工作台。左侧任务记录支持搜索和状态筛选；新建页面提供需求输入、
本地草稿与 Ctrl/Cmd+Enter 提交。选中任务后，主区域显示执行计划、状态摘要与
用量，再通过「执行过程 / 代码改动 / 验证结果」页签查看详细信息。
依赖图折叠展示，步骤详情按需打开，宽屏可在右侧查看。

主视图按 `step_id` 选择最新尝试；同一尝试号的后续记录覆盖前一条。
最新尝试没有产物时不会回显旧补丁，选中无产物节点也不会借用其他节点产物。
验证只将显式 `pass` 标为通过，缺失或未知 verdict 显示无有效结论。
原始步骤记录仍可在详情中审查。

界面分别呈现执行完成、产物审阅和测试基线结果。代码改动明确标注尚未应用，
测试结果注明执行的是基线快照；当前 API 没有补丁应用、审批或恢复任务操作，
前端仅提供取消执行与复制需求新建任务。

### 页面布局

概览、上下文、评测、可观测性与设置使用 `page-stack` 管理区块间距，统一为 16px；卡片自身不再叠加区块外边距。上下文能力按屏宽排列，压缩与缓存并排对齐，窄屏改为单列。指标快照和供应商接入说明默认折叠，字段校验与费用 / 重启提示仍直接显示。

### 后端设置契约

设置页分为后端连接、模型供应商、后端配置、外观、数据、关于。`api/settings_routes.py` 提供读取与部分更新，`settings_store.py` 负责字段校验、密钥脱敏、revision 并发检查和原子文件持久化；`get_settings()` 在启动时合并覆盖值，运行实例不会热切换。值、启动值、schema、密钥存在标记、供应商预设与重启状态通过同一响应返回。

`models.providers` 支持动态供应商 ID，保留原有三个内置配置路径。网关按协议选择 `ConfiguredProvider` 或 `AnthropicProvider`，处理认证与参数差异；原生 Messages 的工具与用量转换为统一 `ChatResult`。模型路由仍使用 `供应商ID:模型名`。接入操作及协议边界见 [README 配置](../README.md#配置)。

前端使用共享页面编辑会话，保留分区之间的未保存值，提交只包含改动。密钥从服务端不可读，浏览器不持久存储；带认证的 SSE 使用 fetch ReadableStream 并复用去重 / 回放逻辑。静态 ES 模块和样式使用一致版本参数，升级时整体更新，避免旧 API 模块与新页面混用；Node 测试沿用同一版本以保持 store 单例，导入图检查按 URL 解析文件路径。

### 可访问性

- **焦点管理**：弹层用 `activateModal`（保存并恢复焦点、滚动锁定、Esc 关闭、
  Tab 陷阱）；`:focus-visible` 而非 `:focus`，鼠标点击不留焦点环。
- **读屏**：toast 分级 —— 普通态 `role="status"` + `polite`，错误态
  `role="alert"` + `assertive` 立即打断；内联 `alert` 用 `role="note"` 不打断。
- **键盘**：skip-link 作为第一个 Tab 位；表格行可 Enter/Space 激活；
  标签页遵循标准 `role="tablist"` 左右方向键交互。
- **动效**：`prefers-reduced-motion: reduce` 下所有动画令牌归零。
- **对比度**：语义色按 WCAG AA 选定，暗色主题单独重新绑定而非反相。

### 响应式

桌面优先，反向覆盖。≤1023px 侧栏转为抽屉；≤767px 表格通过
`data-label` 转为卡片（表头与单元格标签一一对应）；触摸目标在中等断点
升至 ≥38px；≥1600px 放大留白。另含横屏手机与 `forced-colors` 支持。

### 任务 DAG 可视化

模块划分刻意让**布局与 DOM 解耦**：

| 文件 | 职责 |
| --- | --- |
| `web/graph.js` | 纯函数：拓扑分层、几何布局、事件叠加、diff 解析、SVG 渲染 |
| `web/js/pages/workbench.js` | 副作用：页面生命周期、SSE 订阅、节点详情面板 |

`graph.js` 不碰全局 `document`，因此可以用 `node web/graph.test.js`
直接跑 46 个断言，不需要浏览器、不需要 JS 测试框架。

**布局算法**：列 = 拓扑层、行 = 层内序号。层号取**最长路径**而非最短 ——
取最短会让汇合节点与其前驱同层，边的方向感就地破坏。层内按父节点
行号均值（barycenter）排序以减少边交叉。对线性主链，
这个算法退化为一条水平直线，正是希望读者第一眼看到的东西。

**同步策略：乐观更新 + 权威覆盖**。

```
SSE node.* 事件 ──applyEvent()──> 图状态 ──paintDag()──> SVG（即时）
GET /tasks/{id} ─renderDagFromNodes()─> 图状态 ──paintDag()──> SVG（权威）
```

两条路径都写进同一份 `state.graph`。为什么要两套：SSE 是流式的，
但 `GET /tasks/{id}` 只在任务结束时刷新。若只依赖后者，执行过程中
节点不会变色；若只依赖前者，一次丢事件就会让界面停留在错误状态。
**乐观更新给实时性，权威覆盖给自愈能力**。

**节点状态 → 视觉**。这里有一份**跨语言契约**需要特别说明，因为它是
本项目唯一一处「Python 产出字符串、JS 消费」的接口，中间**没有类型系统兜底**。

`StepStatus` 有 8 个成员，前端需要三张映射表把它们翻成视觉：

| 映射表 | 作用 | 漏登记的后果 |
| --- | --- | --- |
| `STATUS_GROUP` | 状态 → 视觉分组 | **静默降级为「待执行」** |
| `STATUS_LABEL` | 状态 → 中文标签 | 界面回显英文枚举名 |
| `AGENT_COLOR` | 角色 → 配色 | 未登记角色共用灰色 |

「静默降级」是这个接口最危险的地方：漏一个状态**不会报错**，
只会把「验证未通过」渲染成「还没开始跑」——比不显示更误导。
类似地，`AGENT_COLOR` 的键名一度写成 `coordinator`（枚举里是
`orchestrator`），导致编排器节点永远退成灰色，而编排器恰恰是 DAG 图上
唯一必然存在的节点。

因此前端**不手抄词表**，而是由 Python 侧导出、前端逐个断言：

```
devagent/enums.py
      │  tests/conftest.py::contract_words_path（pytest session fixture）
      ▼
web/test_contract_words.json          ← 派生文件，已 gitignore
      │  web/graph.test.js 读取
      ▼
逐成员断言 StepStatus / AgentType 全集都被覆盖
```

链路两端各有一道保险：

- `tests/unit/test_node_contract.py::TestCrossLanguageWordlist` 断言导出
  内容与**当前**枚举完全一致 —— 防止有人改了枚举却没重跑，导致前端
  拿着旧词表空跑通过；
- `make web-check` 依赖 `web-words` 目标，总是先重新导出，不依赖
  「记得先跑过 pytest」这种口头约定。

新增枚举成员而忘记登记前端时，`web/graph.test.js` 会立即变红并指出
是哪个成员、后果是什么。

**其他视觉约定**：`backtracked` 单独成组而非并入 `failed` ——
它表示「判定未通过、将回退重跑」，是一次仍在进行中的过程；
混在一起会让读者误判任务已经失败。`ready` 也单独成组（虚线边框），
与「还没轮到」的灰色区分开。`attempt > 1` 时显示 `×N` 徽标。

注意 `backtracked` **不是** `StepStatus` 成员（枚举里是 `rejected`）：
它只存在于事件层，是 `applyEvent` 收到 `node_verdict: reject` 时的派生态，
语义比 `rejected` 更具体。这意味着**只看 `/tasks/{id}` 快照是看不出回退的** ——
快照刷新会把节点覆盖成 `rejected` 或 `pending`，回退语义只在事件流里。

**回退路径**通过节点的 `attempt` 递增呈现，不重画整张图 ——
`renderDag` 按节点 id 复用 `<g>` 元素，只改 class 与文本，
长任务下不产生 DOM 抖动。

**diff 查看器**：点击节点展开详情，从 `steps[].output` 的
Markdown 中抽取 ```` ```diff ```` 围栏并逐行着色（增绿删红，
遵循 git 通行约定）。

两处**必须用真实数据验证**的契约（都是踩过的坑）：

- `step_id` 形如 `task_xxx:N1`，节点 id 是 `N1`，**必须后缀匹配**；
- Coder 输出的 diff 围栏**不含** `+++ b/path` 头，文件名只在
  Markdown 标题 `## 1. src/x.py` 里，因此文件名解析是三级回退。

布局库的选型理由（为何不用 d3/mermaid/cytoscape）见
[ADR-0010](adr/0010-前端DAG自研层次布局.md)。
