# 第一部分：面试深挖题库

## A. 上下文工程（8 题，重中之重）

### A1. 上下文工程和提示词工程的区别？为什么强调它？
**框架**：静态写法 vs 运行时调度系统。上下文工程决定「此刻给模型看什么」，
涉及装配/压缩/隔离/预算四件事，是工程问题而非文案问题。

### A2. 上下文越长效果越好吗？
**框架**：不是。① lost-in-the-middle（中间信息被忽略）② 无关信息稀释注意力、诱发幻觉
③ 成本延迟上升。所以我的策略是「精准投喂 + 位置编排」。

### A3. 你的上下文装配算法是怎么设计的？
**框架**：加权打分（相关性 + 时效 + 依赖 + 信息密度 − 冗余），
带冗余惩罚的贪心选择（类 MMR），外加位置编排（硬约束放头、最新状态放尾）。

### A4. 上下文压缩会丢关键信息吗？怎么保证不丢？
**框架**：会。三条措施：① 只在步骤边界压缩，不在推理中途压
② 用结构化 schema（决策/产物/约束/待办）而非自由摘要
③ 硬约束与验收标准永不进入压缩区。

### A5. 多 Agent 之间上下文怎么同步？为什么不用共享？
**框架**：不共享原始上下文，用结构化握手机制传摘要+引用。
共享会导致污染（Coder 调试噪音干扰 Reviewer）、膨胀、角色混淆。

### A6. 你怎么衡量上下文策略的效果？
**框架**：对照实验。A 组全量塞入 / B 组仅压缩 / C 组完整上下文工程，
对比首pass率、成本、上下文效率。C 组成本最低成功率最高，用数据说话。

### A7. 为什么关键信息要放首尾？
**框架**：模型对序列首尾的注意力权重更高（lost-in-the-middle 现象的应对）。
我把硬约束放头部、最新任务状态放尾部，中间放辅助材料。

### A8. 单个 Agent 上下文超预算了怎么办？
**框架**：三层递进：装配选出最相关的 → 不够压缩历史为结构化摘要 →
再不够指针化（只留引用，按需回捞）。硬约束永不压缩。

## B. 多 Agent 架构（7 题）

### B1. 多 Agent 是不是过度设计？
**框架**：分场景。有对比实验数据；保留单 Agent 降级模式；按复杂度选拓扑。
（这题答好能直接证明工程成熟度）

### B2. 为什么用 Hierarchical 而不是 Peer-to-Peer？
**框架**：全互联消息组合爆炸、责任不清、难调试。Supervisor 集中调度状态清晰、可追踪、易恢复。

### B3. Orchestrator 为什么自己不做设计/编码？
**框架**：职责边界。又当运动员又当裁判会产生自评偏差。它只规划调度，验证交给独立的 Verifier。

### B4. 为什么 Verifier 要用不同模型？
**框架**：避免同模型同偏差（共同盲区）。交叉验证 + 不给它看 Coder 的自我辩解，
只看客观证据（验收标准 + 实际产出 + 测试结果）。

### B5. Agent 之间怎么传信息？为什么不传自然语言？
**框架**：强类型结构化消息。理由：可校验、防歧义、可压缩、可追踪、可程序化处理。

### B6. Agent 互相推诿/循环怎么办？
**框架**：DAG 显式依赖 + Agent 调用图循环检测 + 重试上限 + 结构化反馈（明确要改什么，不空转）。

### B7. 什么情况下你会退化成单 Agent？
**框架**：任务阶段单一（只需一次 LLM 调用）、上下文小且无污染风险、
延迟敏感场景。这时多 Agent 的编排开销不划算。

## C. 可靠性与工程（7 题）

### C1. 怎么防止 Agent 谎报完成？
**框架**：不采信自述。① 测试即事实（沙箱实跑）② 证据链（改动↔验收标准映射）
③ 独立 Verifier ④ 交叉审查。

### C2. 失败后怎么处理？为什么不是简单重试？
**框架**：Reflexion。分析失败证据 → 生成结构化「教训」→ 注入下次上下文 →
重试；连续失败则升级模型/换方案/人工介入。盲目重试会重复踩坑。

### C3. 任务中断了怎么恢复？
**框架**：当前内存 checkpoint 保存已验证节点及产物，同一进程内可恢复；回退会作废相关检查点。跨进程恢复需要持久化实现和输入版本校验，尚未完成。测试重跑使用新的基线快照。

### C4. 成本怎么控制？
**框架**：三层——模型分级路由、上下文压缩、成本熔断。
收益需要在固定数据集和模型配置上与基线实测，目前没有可引用的成本倍数。

### C5. 沙箱安全怎么做的？为什么不用 Firecracker？
**框架**：Docker + 资源限制 + 网络隔离 + 只读挂载 + 非 root + 超时强杀 + 审计日志。
microVM 更安全但启动慢、复杂度高，作为演进方向，当前场景 Docker 是平衡点。

### C6. 怎么排查一个任务为什么失败？
**框架**：全链路追踪。每个 LLM 调用/工具调用/上下文装配都是 span，
能看到具体哪一步、输入是什么、token 多少、为什么路由到该模型。

### C7. 你的系统和企业级 AI 平台差在哪？
**框架**：诚实列出——多租户、权限、SLA、灰度发布、大规模并发。
说明这是个人项目合理取舍，并说明如果要补你会怎么补（展示成长性）。

## D. 评测与前沿（8 题）

### D1. 你怎么评估 AI 系统的好坏？
**框架**：三层指标。任务级（成功率/首pass率/成本）、轨迹级（步骤合理性/工具准确率/
上下文效率）、质量级（测试通过率/需求覆盖率）。

### D2. 为什么需要轨迹级评测？只看结果不行吗？
**框架**：不行。Agent 可能「蒙对结果但过程荒谬」，这种在真实场景会翻车。
轨迹评测能发现「走了冗余弯路」「工具调用浪费」等问题。

### D3. LLM-as-Judge 有什么问题？怎么解决？
**框架**：位置偏差、长度偏好、自身能力上限。解决：双向评估（换序再评）、
多 Judge 投票、人类标注校准。这是业界开放问题，能讨论说明紧跟前沿。

### D4. 什么是 Eval-driven Development？
**框架**：像单元测试一样对待评测。Golden Set + CI 集成，每次改动自动跑评测，
防回退。AI 系统最大的坑是「改了 prompt 不知道变好还是变坏」。

### D5. 模型路由怎么设计的？
**框架**：复杂度评分（推理深度+上下文规模+工具调用数+失败历史）→ 分档选模型。
失败自动升级。记录成本可量化。

### D6. 你怎么看 Agent 的未来趋势？
**框架**：① 上下文工程成为核心 skill ② 从「单次调用」到「长时任务状态管理」
③ 评测/可观测成为刚需 ④ 小模型 + 路由的成本优化 ⑤ Agent 间标准协议。
（展示技术视野，但别空谈，结合自己项目的取舍说）

### D7. 你的项目里有什么是你自己想到的、不是照搬的？
**框架**：举例：上下文预算的动态回流、Verifier 不给看自我辩解、
带冗余惩罚的贪心装配 + 位置编排。说明设计动机来自实际踩坑。

### D8. 如果让你重做，你会改什么？
**框架**：诚实反思。如「一开始没做评测，后面无法量化优化效果，返工了很多」——
展示复盘能力和工程成熟度。

## E. 岗位专项（AI 辅助开发 + coding 工具）

### E1. 你在开发这个项目时怎么用 AI 工具的？
**框架**：具体列举——生成单测、Code Review、重构建议、文档生成、
疑难 bug 的排查思路。强调「我有判断地使用，不是盲信 AI 输出」。

### E2. 用 AI 工具提效了多少？怎么量化？
**框架**：给出对比数据。如「某模块开发从 X 天到 Y 天」「单测覆盖率从 A% 到 B%」
「Code Review 发现的问题数」。有数字才有说服力。

### E3. AI 生成的代码你怎么保证质量？
**框架**：四道关卡——类型检查/静态分析、单元测试、人工 Review、
CI 门禁。强调「AI 产出必须过质量门禁才能合并」。

### E4. 你怎么看待 AI 辅助开发的边界？
**框架**：AI 擅长样板代码、测试、重构、文档；不擅长复杂业务判断、
跨模块架构决策、模糊需求。我的用法是「AI 做执行，我做判断」。

# 第二部分：简历项目描述

## 版本一：标准版（推荐）

---

**多 Agent 协作的智能软件研发助手** ｜ 个人项目 ｜ 全栈开发

**项目背景**
面向研发场景，构建由多个专职 Agent 协作的自动化研发系统，输入需求即可完成
「需求澄清 → 方案设计 → 代码产物 → 基线测试 → 独立验证」编排，补丁应用尚待实现，重点研究多 Agent 场景下
**上下文失控、幻觉传播、成本不可控、效果不可评估**四大生产级难题。

**核心工作**
- **设计并实现上下文工程体系**（项目核心竞争力）：构建装配/隔离/压缩/预算/路由五层能力。
  提出「加权打分 + 冗余惩罚」的上下文装配算法，结合位置编排对抗 lost-in-the-middle 现象，
  在预算约束下实现信息的精准投喂。
- **设计 Hierarchical Supervisor 多 Agent 拓扑**：Orchestrator 负责规划调度（不参与执行，
  避免自评偏差），各专职 Agent 分工；引入独立 Verifier 层，用隔离的输入做交叉验证，
  阻断幻觉沿链条传播。
- **设计结构化握手机制**：Agent 间以强类型消息（含验收标准、证据、上下文引用）通信，
  替代自然语言传递，实现可校验、可压缩、可追踪的协作协议。
- **构建可靠性保障体系**：Reflexion 失败反思（失败→教训→注入下次上下文）、
  已验证 DAG 节点的进程内 Checkpoint 恢复、循环检测、成本熔断。
- **搭建 Eval-driven 评测体系**：构建 Golden Set，从任务级/轨迹级/质量级三维度量化，
  集成 CI 防止效果回退。
- **实现模型分级路由**：按复杂度评分动态选择模型，结合上下文压缩，
  通过 token 与费用账本为后续成本对照实验提供数据。

**技术栈**
Python / FastAPI / SQLAlchemy（SQLite / PostgreSQL）/ Docker 可选 / Tree-sitter /
自研观测（OpenTelemetry 可选）/ 原生 JavaScript ES Module + CSS + SSE

**量化成果**（示例，请用你的真实数据替换）
- 单任务平均 token 成本相对基线的变化：待固定数据集实测后填写
- 多阶段任务首次通过率提升约 X 个百分点
- 上下文平均压缩比达 X:1，且成功率无下降

## 简历撰写要点

1. **「上下文工程」必须出现在简历里**——这是 2026 年最值钱的关键词，且你的项目真的有
2. **量化指标必备**——没有数字的描述会被认为「只是跟教程做的」

# 第三部分：面试演示脚本（现场 demo 建议）

**演示原则**：不要现场即兴，用**预置的、可复现的任务**。

### 演示流程（8-10 分钟）

1. **任务输入**（30s）：输入一个预置需求，如「给用户接口加分页并补测试」
2. **协作可视化**（2min）：展示 DAG 执行、各 Agent 分工、实时进度
3. **上下文可视化**（3min）★ 杀手锏：
   - 展示 Coder 拿到的上下文（哪些文件、多少 token）
   - 对比「不做上下文工程」时的上下文（巨长、含大量无关内容）
   - 展示压缩比与预算分配
4. **失败与恢复**（2min）：展示一个 Verifier 打回 → 带反馈回退 → 修复通过的过程
5. **评测报告**（2min）：展示 Golden Set 的评测结果与历史对比
6. **成本面板**（1min）：展示 token 消耗、模型路由分布、成本对比

**准备一个录屏备份**，防现场网络/API 问题。
