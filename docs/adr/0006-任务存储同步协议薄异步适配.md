# ADR-0006：任务存储用「同步协议 + 薄异步适配」而非全异步

- **状态**：已采纳
- **日期**：2024-10
- **相关**：`src/devagent/api/store.py`、`src/devagent/api/service.py`、`src/devagent/db/`

---

## 背景

任务需要落库，主要有三个动机：

1. **进程重启不丢任务**。默认部署是单进程 uvicorn，重启即清空内存。
2. **SSE 历史回放要真正可靠**。现在内存 `EventBus` 的缓冲只有 500 条，
   且随进程消失。任务跑几分钟、用户晚半小时才打开页面时，前端会看到空时间线。
3. **多实例部署**。两个 uvicorn 实例共享一份任务状态，内存实现做不到。

已有实现是 `InMemoryTaskStore`，它**同步、零依赖**，且是 353 个测试的基础。

新增一个 `SqlTaskStore` 就必然引入一个冲突：**SQLAlchemy 的 `AsyncSession`
是异步的，而现有协议与全部调用代码是同步的。**

## 决策

**保持 `TaskStore` 协议不声明 `async`，用一个极薄的适配器吸收差异。**

```python
async def _maybe_await(value: Any) -> Any:
    if inspect.isawaitable(value):
        return await value
    return value
```

- `InMemoryTaskStore` 继续是普通 `def`；
- `SqlTaskStore` 是 `async def`；
- `TaskService` 的所有存储调用统一走 `_maybe_await(store.xxx(...))`。

同时给 `TaskStore` 加 `@runtime_checkable`，让「实现是否满足协议」可被测试断言。

## 备选方案与权衡

### 方案 A：把协议整体改成 `async def`（**否决**）

这是最"自然"的做法 —— 既然 SQL 是异步的，就让所有人都异步。

**为什么否决**：

1. **测试成本被放大**：内存实现是纯逻辑、无 I/O 的。改成 `async def` 后，
   所有直接调用它的单测都必须变成协程；原本同步的断言逻辑被迫进入事件循环。
   本项目 353 个测试里有相当一部分只碰内存实现，改动面过大。
2. **为每次调用引入无谓开销**：`asyncio` 下创建一个协程对象 + 调度一次是有
   实际成本的（微秒级）。对纯内存字典操作来说这是纯亏损。
3. **它并没有解决真正的问题**：真正要的是「上层代码不关心实现是同步还是异步」，
   而不是「让同步实现假装成异步」。方案 A 把复杂度平摊到了所有调用方，
   方案 B 把它集中在**一个函数**里。

### 方案 B：薄适配器（**采纳**）

代价只有一次 `inspect.isawaitable()` 判断（纳秒级），换来：

- 两种实现共用同一套调用代码；
- 纯逻辑单测保持同步；
- 未来接入 Redis / 远程存储时，异步实现可以零摩擦插入。

### 方案 C：用类型参数让适配器「泛型化」（**否决**）

看起来更优雅：`async def _maybe_await[T](value: T | Awaitable[T]) -> T`。

**为什么否决**：入参的联合类型无法在运行期收窄 —— 一个 `dict` 和一个返回
`dict` 的协程在类型上都是合法的 `T`，mypy 会把返回类型推成 `Any` 或要求
调用方 `cast`。与其造一个看起来漂亮但实际不解决问题的泛型，不如
**在边界处显式收窄**：`_as_dict` / `_as_dict_list` 两个小函数各做一件事，
调用点干净，mypy strict 也能通过。

这体现了本项目的一个偏好：**宁可写三个直白的小函数，也不要一个"聪明"的抽象。**

### 方案 D：让 `SqlTaskStore` 用同步驱动（如 `psycopg2`）包一层（**否决**）

技术上可行：同步 ORM 在 `asyncio` 里跑在 `run_in_executor` 线程池里即可。

**为什么否决**：

- 每个 DB 操作都要 **跨线程**，在 FastAPI 的异步请求路径上引入线程池排队；
- 连接池的线程安全问题需要额外处理；
- 项目已全面 async（模型调用、事件总线、SSE），**在这一层退回同步**会造成
  一个突兀的同步孤岛，后续扩展（如流式读取大量事件）会很难受。

### 方案 E：不落库，用 Redis 存任务（**否决**）

`RedisConfig` 已经存在，看起来可以复用。

**为什么否决**：

- Redis 适合存**短生命周期、结构简单**的数据。任务记录包含嵌套的
  steps / nodes / context_metrics，用 Redis 存要么序列化成一个大 JSON
  （失去按状态查询的能力），要么手工建模 hash 结构（等于自己实现一个数据库）；
- **事件日志需要按序读取与范围查询**，Redis List 能做但功能弱于 SQL；
- 项目已经把 Postgres 作为"生产存储"的既定假设写进了配置与文档，
  引入 Redis 作为任务存储会形成**两个持久化系统**，增加运维负担。

Redis 的位置仍然是缓存/队列（`RedisConfig` 保留），而不是事实数据源。

### 关于自动清理：**不做**（刻意）

任务数据只增不删。生产环境应有保留策略（如 30 天），但这是**运维策略**，
不是应用逻辑。

如果硬编码一个 TTL，需要长期留存审计记录的部署就得改代码；而反过来，
只需要清理的部署写个 cron 调用 `delete` 即可。**把策略留给外部，
只提供机制**。

## 后果

### 正面

- 353 → 386 个测试，持久化层有 33 个独立测试（不依赖外部数据库）
- 默认配置仍是 `memory`，贡献者 clone 后**零配置**即可跑通
- 切换后端只改一个环境变量：`DEVAGENT_STORAGE__BACKEND=sql`
- 事件历史跨进程重启可回放，SSE 的可靠性承诺从"尽力而为"变成"真的"

### 负面 / 技术债

- `_maybe_await` 让「存储调用是否真的被 await」在阅读时不够直观 ——
  缓解手段是文档与协议注释，以及一条专门锁住"内存实现必须保持同步"的测试
- `SqlTaskStore` 的 `save` 是「先查后改」而非 `ON CONFLICT` upsert。
  多了一次查询，换来跨方言一致性。**在高并发写同一 task_id 时存在竞态**，
  但当前每个任务只由单个 `TaskService` 实例串行写入，不构成实际问题
- 没有 Alembic 迁移文件（测试用 `create_all`）。生产演进 schema 前必须补上

### 已修正的实现缺陷

引入这一层时暴露的 3 个真实缺陷（详见 [CHANGELOG](../../CHANGELOG.md)）：

1. `pyproject.toml` 缺少 `[db]` extra —— 而报错文案让用户去执行一个
   **照着做必然失败**的安装命令
2. `Database.__init__` 丢弃惰性导入的 `AsyncSession` 后引用模块级同名符号
   → 运行期 `NameError`。这意味着**该实现此前从未被真正执行过**
3. `TaskStore` 未声明 `@runtime_checkable`，协议符合性无法在运行期验证

第 2 条尤其值得记住：**写了但从未被执行的代码，等同于没有代码。**
