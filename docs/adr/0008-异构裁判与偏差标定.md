# ADR-0008：异构裁判 + 偏差标定，而非单纯的「换个模型当裁判」

- **状态**：已采纳
- **日期**：2024-10
- **相关**：`src/devagent/evaluation/heterogeneous.py`、`src/devagent/evaluation/factory.py`、`src/devagent/evaluation/runner.py`、`tests/unit/test_heterogeneous_judge.py`

---

## 背景

ADR-0005 用「双向评估」对冲了 LLM-as-Judge 的**位置偏差**与**单次采样噪声**。
但它对冲不掉最根本的一类偏差：**自我偏好（self-preference）**。

实测与文献都指向同一个现象：模型给自己（或同族模型）的输出打分，
系统性高于给其他族模型的输出打分。幅度在 1-5 分制上常见 0.3～1.0 分。

这在本项目里不是假设性问题 —— 默认配置下它**必然发生**：

```
DEVAGENT_ROUTING__MEDIUM_MODEL   = deepseek:deepseek-chat   # 候选模型
DEVAGENT_EVALUATION__JUDGE_MODEL = deepseek:deepseek-chat   # 裁判模型
```

同一行配置，候选和裁判是同一个模型。此时 `mean_judge_score` 再高也
说明不了系统变好了 —— 它可能只是裁判偏心。

**问题的本质不是「换个模型」，而是「你不知道偏差有多大」。**

如果只是把裁判换成 qwen，你得到了一个更可信的数字，但你无法说出
旧数字偏了多少，也无法在你只有同族模型可用时（国内 API 场景很常见）
给出任何经过处理的结论。

## 决策

引入 `JudgePanel`，把裁判从「一个模型」升级为「**主裁判 + 可选异构参考裁判 + 标定出的偏差**」，
并把偏差**写进评测报告**。

三种情形的处理**刻意不同**：

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| 主裁判与候选**异构** | 直接用，标记 `judge_relation=heterogeneous` | 最理想，无需校正 |
| 主裁判与候选**同源** + 已有可靠标定 | 按偏差扣减，标记 `calibrated=true` | 有依据的校正 |
| 主裁判与候选**同源** + 无标定 | **不校正**，标记 `uncalibrated_self_preference=true` | 见下文 |

关键点：**异构判定按「模型族」而非模型名**。

```
deepseek-chat / deepseek-reasoner / deepseek-coder  ─┐
                                                    ├─→ family: deepseek
qwen-plus / qwen-max / qwen-turbo  ─────────────────┼─→ family: qwen
glm-4 / glm-4-plus  ────────────────────────────────┴─→ family: zhipu
```

`deepseek-chat` 与 `deepseek-reasoner` **名字不同但同族**，
把它们当作异构裁判是自欺欺人 —— 这是本模块最容易出错的一点。

标定的可靠性门槛 `_MIN_CALIBRATION_SAMPLES = 20`：

偏差是均值层面的量，标准误约 `sigma / sqrt(n)`。取 `sigma ≈ 0.8`
（1-5 分制下裁判分数的典型标准差），要让标准误降到 0.2 以内需 `n ≈ 16`；
取 20 留余量。样本不足时 `trustworth == False`，**不用于校正**。

## 备选方案与权衡

### 方案 A：只把裁判换成异构模型，不做标定（**部分否决**）

最省事的做法：把 `JUDGE_MODEL` 默认值改成 `qwen:qwen-plus`，问题「看起来」解决了。

否决理由有三层：

1. **它把问题藏起来了，而不是解决了。** 你得到一个新数字，但不知道旧数字
   偏了多少，也没法回答面试官那句「你怎么证明裁判是公正的」。
2. **国内 API 场景下异构裁判不一定可得。** 用户可能只有 DeepSeek 一个 key。
   此时方案 A 完全失效，而标定至少能给出一个「已知偏差」的量级。
3. **异构不等于无偏。** 换一个族只能消除*自我*偏好，跨族的评分尺度差异
   （有的模型天生打分松）依然存在。标定是唯一能测量这个差异的手段。

不过方案 A 的**合理内核被吸收了**：`JudgePanel` 在检测到主裁判已异构时，
直接跳过校正、只打标签。省下的算力用在真正需要的地方。

### 方案 B：用多个裁判投票取平均（**否决**）

跑 3 个裁判，取中位数。

否决理由：**成本线性增长，但偏差不会抵消。**

投票消的是**随机噪声**，而自我偏好是**系统性偏差** —— 系统性偏差在
取平均时不会变小，只会被平均进去。若 3 个裁判里有 2 个是同族，
结果比单裁判更糟：它披上了「多数决」的外衣，可信度看起来更高但实际没有。

正确的做法是先测偏差再扣减（本 ADR 的方案），而不是试图用数量掩盖偏差。

### 方案 C：构造专门的标定样本集（**否决**）

人工写 50 条「标准答案 + 已知分数」的样本，用它标定裁判。

否决理由：**标定样本的分布必须贴近真实评测分布，否则标定结果不可迁移。**

人工构造的样本天然偏「干净」：目标明确、答案标准。而真实评测里
候选输出带着各种模棱两可和部分正确 —— 裁判在这些样本上的偏差
与在干净样本上的偏差**不是同一个数**。

最终采用了「用真实 golden set 的**验收标准文本本身**作为探针」的做法：
内容中性，但分布与评测一致，且能在跑昂贵的编排之前完成标定。

### 方案 D：在线累积标定，随评测推进动态更新偏差（**部分采纳**）

`JudgePanel` 保留了 `_history` 字段记录 `(primary, reference)` 分数对，
但**不参与分数校正**，只作为诊断数据。

理由：在线累积的偏差估计在评测前几十个样本上极不稳定，
用它去校正当前样本会造成「前半段分数偏高、后半段偏低」的伪趋势 ——
这比不校正更危险，因为它看起来是一条有意义的曲线。

因此校正只用**评测开始前**一次性标定出的偏差。`_history` 留给
后续做「偏差是否随样本变化」的分析。

### 方案 E：用未标定的默认常数扣分（**明确否决**）

例如「知道模型平均高估 0.5 分，那就统一减 0.5」。

这是本 ADR 里**最需要警惕**的方案。否决理由：

**用未经验证的常数扣分，比不扣分更糟 —— 它让分数看起来已经被修正过。**

未被修正的高分，读者会警惕；被「修正」过的高分，读者会信任。
如果这个常数是拍脑袋来的，你只是把一个可疑的数字包装成了可信的数字。

所以第三种情形（同源 + 无标定）选择**如实返回 + 显式标记**，
并在日志里给出可操作的修复建议（配置异构裁判）。

### 方案 F：把偏差校正放在报告层而非 `JudgePanel` 里（**否决**）

技术上可行：`EvalReport` 拿到原始分数和偏差，在计算 `mean_judge_score` 时扣减。

否决理由：**校正必须发生在 `JudgeResult` 层，否则会污染下游所有消费者。**

`passed` 字段是根据 `overall` 与阈值比较得出的。若只改 `overall` 不改
`passed`，就会出现「分数 2.8 但 passed=True」这种自相矛盾的结果。
`_apply_calibration()` 因此在扣减每个维度分数的同时，
**用主裁判自己的 `_pass_threshold` 重新计算 `passed`** —— 这两件事必须原子地一起做。

## 后果

### 正面

- 自我偏好偏差从「不可见的假设」变成「报告里的一个字段」（`calibration.bias`）。
- 同源 + 已标定时分数被有依据地修正；`passed` 同步重算，不会自相矛盾。
- 默认配置下的风险被**主动暴露**：CLI 与 API 启动评测时若检测到同源，
  会打 `judge_self_preference_risk` 警告，而不是静默给一个偏高的分数。
- 配置了同族参考裁判时直接拒绝并警告（`reference_judge_same_family`），
  避免「看起来做过标定、实际偏差恒为 0」的假象。

### 负面

- 标定需要额外一轮 `样本数 × 2` 次裁判调用。`calibrate=False` 可关闭。
- 模型族表是**硬编码**的。新模型需要手工登记，否则 `model_family()`
  会退回按名称前缀推断，可能误判。
- 偏差被假设为**加性且全局**的（所有维度减同一个数）。
  真实偏差可能与维度相关（例如「完整性」维度偏得更多），
  当前实现不做区分 —— 这是一个已知的简化。

### 技术债

1. 样本不足时 `uncalibrated_self_preference` 标记会出现在**每一个** `JudgeResult` 上，
   报告会显得很吵。可考虑在报告层聚合为一条提示。
2. `_history` 目前只写不读，属于预留。若长期不用应删除。
3. 偏差的维度相关性未建模（见上）。
