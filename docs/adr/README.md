# 架构决策记录（ADR）

本目录记录 DevAgent 的**重大技术决策**。

## 为什么要写 ADR

代码告诉你「是什么」，ADR 告诉你「为什么」以及「为什么不选另一个」。
后者往往更有价值——因为半年后最常被问到的问题是：

> "这个看起来更简单的方案，当时为什么没选？"

如果答案已经丢失，要么重复踩坑，要么做出矛盾的改动。

## 格式约定

每篇 ADR 包含：

| 章节 | 内容 |
| --- | --- |
| 状态 | 已采纳 / 已废弃 / 被 ADR-XXXX 取代 |
| 背景 | 面临什么约束与问题 |
| 决策 | 最终选了什么 |
| 备选方案与权衡 | **每一条被否决的路线及其原因**（最重要） |
| 后果 | 正面、负面、技术债 |
| 相关 | 代码位置与关联 ADR |

## 撰写新的 ADR

1. 复制最近一篇的结构
2. 编号连续（`0006-...`）
3. 文件名用中文短标题，`-` 连接
4. 提交时在本文档的索引表中增加一行
5. **必须**有「备选方案与权衡」章节，且写清每条被否决的原因

### 什么时候需要写 ADR

- 引入 / 移除依赖
- 改变公共接口（`models/domain.py` 中的模型）
- 调整核心算法（上下文装配、DAG 调度、评测聚合）
- 安全相关的默认值变更
- 任何"未来有人会问为什么"的决定

### 什么时候不需要

- Bug 修复（除非修复方式体现了重要取舍）
- 代码风格
- 内部重构（不改变行为与接口）
- 文档改进
