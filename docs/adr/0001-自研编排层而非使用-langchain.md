# ADR-0001：自研编排层，而非基于 LangChain / LangGraph

- **状态**：已采纳
- **日期**：2024-10
- **决策者**：核心开发

---

## 背景

项目需要一个多 Agent 编排层，负责：

1. 按 DAG 拓扑序调度，无依赖节点并行执行
2. 节点失败时递归传播到下游，只重跑受影响的子图
3. 验证驳回时回退到上游节点并清除其检查点
4. 每一步精确控制发给模型的上下文（这是项目的核心命题）
5. 全链路埋点：token、成本、延迟、上下文节省率

选型时考察了 LangChain、LangGraph、AutoGen、CrewAI。

## 决策

**自研编排层**，约 600 行，位于 `src/devagent/orchestration/`。

## 备选方案与权衡

### 方案 A：LangGraph

**优点**

- 图状态机是一等抽象，与我们的 DAG 需求天然契合
- 内置 checkpointer、human-in-the-loop、流式输出
- 社区活跃，文档完善

**为什么否决**

1. **上下文构造不透明**。我们要回答「这个 token 为什么进了这次请求」，
   而 LangGraph 的消息管理封装在内部。要精确控制就得绕过它的 state 机制，
   等于只用它的调度器——那不如自己写调度器。
2. **回退语义不匹配**。LangGraph 的 checkpoint 是为「断点续跑」设计的，
   而我们需要的是「驳回后**失效**检查点强制重跑」。前者是恢复，后者是作废，
   语义相反。ADR-0002 记录了踩到的正是这个坑。
3. **失败传播需要自己实现**。LangGraph 不提供「上游失败则递归标记下游跳过」，
   仍要写遍历逻辑。

### 方案 B：LangChain（AgentExecutor）

**为什么否决**

- 抽象层过厚，`Agent` 概念与我们的「强类型结构化握手」冲突
- 链式调用模型难以表达「验证失败回退到任意上游节点」这种非线性的控制流
- 每次版本升级都有破坏性变更，长期维护成本高

### 方案 C：AutoGen / CrewAI

**为什么否决**

- 对话驱动的协作模型，Agent 之间传自然语言长文
- 这恰恰是本项目要**消除**的模式（幻觉传播的温床）
- 无法表达 DAG 依赖与并行调度

### 方案 D：自研

**优点**

- 完全掌控上下文构造，`ContextEngine.build()` 是唯一入口，可精确埋点
- 回退语义按需设计（作废检查点，而非恢复）
- 零框架依赖，`pip install -e .` 后立即可跑，无版本地狱
- 每一行代码都能在面试中解释清楚

**代价**

- 需要自己实现调度、并发、失败传播（约 600 行）
- 没有社区生态，出了问题只能自己修
- 需要自己写并行执行与异常隔离

## 后果

### 正面

- 上下文节省率可被精确量化（`context_compression_ratio` 指标覆盖全部 5 个角色）
- 回退机制正确：`clear_step` 在回退时作废检查点，回归测试守护
- 项目「clone 即跑」，无框架版本兼容问题
- 编排逻辑完全可测：`tests/unit/test_dag.py` 直接构造 DAG 验证拓扑与传播

### 负面

- 无法复用 LangGraph 的 human-in-the-loop、可视化等现成能力
- 新贡献者需要先读约 600 行编排代码（已通过 ADR 与详细 docstring 缓解）
- 并行执行的边界情况（如 `asyncio.gather` 下 contextvar 栈串线）需要自己处理

### 已识别的技术债

- `asyncio.gather` 会破坏 contextvar 的隐式父子栈，因此 `Span` 使用**显式 parent 指针**
  而非依赖 `contextvars`。这是一个真实的实现约束，已在 `observability/tracing.py` 中注明。
