# ADR-0002：上下文装配使用「软打分 + 硬去重」双保险

- **状态**：已采纳
- **日期**：2024-10
- **决策者**：核心开发
- **修正了**：一个导致关键约束被挤占的真实缺陷

---

## 背景

上下文装配算法负责在有限 token 预算内，从候选片段集合中选出最优子集。
打分公式的意图是：高相关、新近、为当前步骤硬依赖的片段得分高；
与其他已选片段重复的片段被扣分。

```
score(chunk) = w_rel · relevance
             + w_rec · recency
             + w_dep · dependency
             + w_den · density
             + w_trust · trust
             - w_red · redundancy_penalty
```

> **注**：早期设计中有一项 `w_auth · authority`（来源权威度），
> 但在实现时未落地 —— 当时的 `ContextChunk` 没有权威度元数据，
> 该权重在配置中不存在。它后来由
> [ADR-0009](0009-提示词注入信任度分级.md) 的 `w_trust · trust`
> 以**更明确的形式**取代：不再是比较来源之间的权威高低，
> 而是标记"这个来源是否受我们控制"。这里保留公式的历史原貌，
> 以免读者误以为当前代码里有一个从未实现的项。

其中冗余惩罚最初设计为**线性**：

```python
redundancy_penalty = w_red * max_similarity_to_selected
```

选择过程是贪心：每轮选当前得分最高的片段，直到预算耗尽。

## 问题

线性冗余惩罚**不足以让重复片段让出位置**。

### 具体场景

假设预算只够放 2 个片段，候选如下：

| 片段 | 相关性 | 与已选片段相似度 | 权重后得分 |
| --- | --- | --- | --- |
| A（已选） | 1.00 | — | — |
| B | 1.00 | 0.95 | `1.0 - w_red·0.95` |
| C（关键约束） | 0.55 | 0.05 | `0.55 - w_red·0.05` |

当 `w_red = 0.4` 时：

- B 得分 = `1.0 - 0.38 = 0.62`
- C 得分 = `0.55 - 0.02 = 0.53`

**B 胜出**。于是第二个片段与第一个 95% 重复，而「必须遵守的关键约束」被挤出预算。

提高 `w_red` 可以修掉这个例子（`w_red = 0.6` 时 B 得 0.43 < 0.53），
但这会同时**过度惩罚部分重叠的合理片段**：两个各自带来新信息、只共享少量术语的片段
会被误伤。线性惩罚无法同时满足两个方向。

### 为什么线性不合适

冗余的边际效用是**非线性下降**的：

- 相似度 0.95 的第二个片段，信息增益 ≈ 0
- 相似度 0.30 的第二个片段，信息增益仍然可观

线性惩罚把这两种情况按比例处理，与真实信息增益的形状不匹配。
指数的形状才对。

## 决策

采用**双保险**设计。

### 第一层：非线性penalty（指数衰减，gamma=4）

```python
redundancy_penalty = w_red * (max_similarity ** gamma)   # gamma = 4
```

`gamma = 4` 的效果：

| 相似度 | 惩罚系数 (sim⁴) |
| --- | --- |
| 0.95 | 0.815 |
| 0.60 | 0.130 |
| 0.30 | 0.008 |
| 0.05 | 0.000006 |

重复片段的惩罚被急剧放大，部分重叠的片段几乎不受影响。
之前的例子在 `w_red = 0.4` 下：

- B 得分 = `1.0 - 0.4×0.815 = 0.674`
- C 得分 = `0.55 - 0.4×0.000006 ≈ 0.550`

……**B 仍然胜出**。

这说明：只要 B 的相关性满分，软打分层面的任何调整都可能被相关性优势抵消。
**光靠打分不足以保证正确性。**

### 第二层：硬去重（Hard Deduplication）

在贪心选择过程中，维护已选片段的**内容指纹集合**。
候选片段在入选前先检查指纹：

```python
def _is_duplicate(chunk: ContextChunk, selected_fingerprints: set[str]) -> bool:
    """内容级去重：与已选片段实质相同则直接丢弃。"""
    return chunk.fingerprint in selected_fingerprints
```

指纹基于规范化后的内容（去空白、大小写归一）生成。
这一步**不参与打分**，是一道无条件的门禁。

于是上面的例子中，B 尽管得分更高，但因为与 A 的相似度超过去重阈值而被直接排除，
C 顺利入选。

## 为什么保留两层

因为它们防的是**不同**的问题：

| 层 | 防的问题 | 失效场景 |
| --- | --- | --- |
| 软打分（指数惩罚） | 部分重叠挤占预算 | 相关性差距过大时压不住 |
| 硬去重 | 实质重复被选中 | 只能处理高度相似的，无法权衡 |

只保留软打分 → 本 ADR 描述的场景会复现。
只保留硬去重 → 大量「中度重叠」片段会耗尽预算，因为它们不算"重复"。

两层叠加后：硬去重兜住底线正确性，软打分负责在剩余空间里做质量优化。
**这符合「正确性用硬约束保证，优化用软目标处理」的一般工程原则。**

## 后果

### 正面

- 关键约束不再因冗余挤占而丢失（有专门的回归测试）
- 部分重叠的合理片段不被误伤（指数曲线在低相似度区接近 0）
- 即便权重配置失误，去重仍能兜底

### 负面

- 硬去重的相似度阈值需要调参，过严会丢弃有价值的近似片段
- 指纹计算有微小开销（可忽略，纯字符串操作）
- 算法从纯贪心变成「贪心 + 门禁」，解释成本略高（已由本文档承担）

### 可测量的证据

`context_compression_ratio` 直方图按 Agent 维度记录压缩比，
`context_utilization` 记录预算利用情况。装配质量的改进可直接从指标观察。
