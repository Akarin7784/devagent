# ADR-0010：前端 DAG 用自研层次布局，不引入图形库

- 状态：已采纳
- 日期：2026-10-07
- 相关：`web/graph.js`、`web/js/pages/workbench.js`、`docs/06-架构说明.md`

## 背景

项目从第一天起就有任务 DAG（`src/devagent/orchestration/dag.py`），但
**前端从未把它画出来**。界面上只有一条按时间排序的事件流：
`node_started → node_finished → node_verdict`，节点之间的依赖关系、
回退路径（`verifier:reject → coder:retry`）全部丢失。

结果是：本项目最核心的卖点 —— 一个有向无环图驱动的编排器，带独立验证层
与结构化回退 —— 在演示时只能靠讲。观众看到的是一串日志，而不是一张图。

因此需要把 DAG 真正渲染出来。核心问题只有一个：**怎么画**。

## 决策

**自研一套约 200 行的层次布局（layered layout），用原生 SVG 渲染。
不引入 d3 / mermaid / cytoscape / elkjs 等任何图形库。**

具体做法：

1. **布局**：`computeLayers` 做拓扑分层（列 = 层，行 = 层内序号）。
   层号取**最长路径**而非最短，保证所有前驱都在更小的层里，边只向右。
   层内用 barycenter（父节点行号均值）排序减少边交叉。
2. **同步**：`buildGraphState` + `applyEvent` 把 SSE 事件映射为图形状态，
   字段与服务端 `orchestrator._emit` 的契约逐字段对齐。
3. **渲染**：`renderDag` 按节点 id 复用 `<g>` 元素，只改 class 与文本。
4. **降级**：布局抛错（如图中有环）时显示提示文案，不白屏。

## 备选方案与权衡

### A. 引入 d3-dag / dagre 做布局

**否决。** dagre 的定位是「通用有向图布局」，它为每个图做力导向式的
迭代优化（排序多轮、坐标细化），代码量以千行计且依赖链长（dagre →
graphlib → lodash）。而我们面对的是**极度受限**的图：

- 节点数是个位到几十（真实任务不会超过 20 个节点）；
- 结构几乎总是一条主链加少量分支（`req → arch → coder → verifier`）；
- 不需要交互式拖拽、不需要折叠、不需要动态增删边的自动重排。

为这种图引入通用引擎，等于为了「几行代码就能画好的直线」去背一个
实现很重的依赖。而且真正的痛点不在布局算法，在**事件同步**——
那是任何图形库都不替你解决的。

### B. 引入 mermaid

**否决，理由更硬。** mermaid 是**声明式**的：给它一段文本，它渲染成
静态图。而我们需要的是**实时更新**——节点状态随 SSE 事件逐秒变化。
用 mermaid 意味着每次事件都要重新生成整段文本、重新解析、重新渲染，
既有性能问题（长任务下每秒重建整图），又会丢失用户交互状态
（hover 到哪个节点、选中了哪个节点）。它的架构与需求方向相反。

### C. 引入 cytoscape.js / vis-network

**否决。** 这两个是**交互式图探索**库（力导向、拖拽、缩放、框选），
强项在「未知结构的网络」。而 DAG 的语义是「有方向的依赖」——
力导向正好会破坏最重要的层次感，让读者自己去猜边的方向。
用它们意味着引入依赖后再关掉大部分能力，只留渲染，那不如自己写。

### D. 用 Canvas 而非 SVG

**否决。** Canvas 在数千节点时才有性能优势，我们最多几十个。
而 SVG 有两个不可替代的好处：① 用 CSS 直接控制节点样式，
主题切换与状态着色不需要重写绘制逻辑；② 原生支持 tabindex / 键盘事件，
可访问性免费获得。用 Canvas 就得自己实现命中检测、焦点管理、
文本换行——为了不需要的性能付出确定性的成本。

### E. 布局用递归而非迭代

**否决。** 递归写法更短，但 DAG 深度理论无上界。3000 节点的链
（不是假想：一个长任务在回退重跑时会产生很深的依赖）会让递归爆栈，
而爆栈的位置在浏览器里极难调试。迭代 + 显式栈没有这个风险。
已用 `test('深链不爆栈')` 锁住这个行为。

### F. 悬空依赖（deps 指向不存在的节点）直接抛错

**否决。** 这看起来更"严格"，但真实场景里它更常见的原因是
**增量推送的时序**：SSE 先发了 `node_started`（带 deps），
而某些 deps 对应的节点还没被前端见到。抛错会让整张图消失；
跳过则只损失一条边，下一个快照就自愈。已用
`test('悬空依赖被跳过')` 锁住。

### G. 只依赖键盘/无交互（纯只读图）

**否决。** 可以，但浪费了图的最大价值。图能回答「哪些节点相关」，
却回答不了「这个节点到底改了什么」——后者需要 diff。因此加了
点击节点展开详情（含代码改动 diff），让图成为**入口**而非终点。

## 后果

### 正面

- 零新增依赖。前端保持「clone 即可打开」的零构建前提，
  没有 `package.json`、没有 `node_modules`。
- 布局逻辑是**纯函数**（`web/graph.js` 不碰 DOM），因此可以用
  `node web/graph.test.js` 直接测，40 个断言覆盖分层、几何、
  事件叠加、diff 解析——不需要浏览器，也不需要 JS 测试框架。
- 增量更新由我们掌控：按 id 复用 `<g>`，长任务下不重建 DOM。

### 负面 / 已知限制

- **层内排序是启发式的**。barycenter 能显著减少交叉，但不保证
  最小交叉数（那是 NP-hard）。对几十个节点的图，肉眼效果足够。
  若未来节点数上到数百，需要换成 Sugiyama 的完整三阶段。
- **不支持拖拽/缩放**。图宽度超出面板时靠横向滚动。对当前规模够用。
- **回退边（`back=true`）会绕行**。目前服务端的 `_emit` 只发节点状态，
  没有显式表达「回退边」的事件；`back` 分支是**防御性实现**——
  一旦后端表达了反向依赖，前端能正确画出。这是一个有意的空实现，
  不是死代码：`edgePath` 的 `back` 分支有测试覆盖，且 `renderDag`
  会据此加虚线样式。
- **DOM 渲染路径未被自动化测试覆盖**。`renderDag` 需要真实 DOM，
  而引入 jsdom 会打破零依赖前提。折中：用 `node --check` 保证语法，
  用一次性 DOM stub 人工验证过真实代码路径（复用 `<g>`、状态着色、
  徽标显隐、失效节点清理均正确），并在浏览器中人工确认过。

### 需要 revisiting 的信号

- 单任务节点数常态超过 100；
- 出现「边交叉导致读者看不懂」的实际反馈；
- 需要 DAG 编辑能力（那时布局必须支持重排）。

## 备注

`step_id` 与节点 id 的匹配规则是本 ADR 附带修掉的一个真实缺陷：
真实 `step_id` 形如 `task_cea6348d2798:N1`，而节点 id 是 `N1`。
早期实现用 `===` 精确比较，导致 diff 面板永远为空——逻辑写对了，
匹配规则错了。这提醒我们：**跨层契约（此处是 step_id 的命名约定）
必须用真实数据验证一次，而不是靠读代码推断**。
